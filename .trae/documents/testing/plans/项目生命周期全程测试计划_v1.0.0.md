# fineSTEM 项目生命周期全程测试计划 v1.0.0

> **文档定位**：本计划定义一种**全新的测试模式——"项目生命周期全程测试"（Lifecycle Journey Test）**。
> 它**不取代**任何既有测试计划（`对话系统回归测试计划_v1.0.0.md`、`SOP_Memory专项`、`ZeroClaw重构专项`等），也**不抛弃**任何既有测试用例。
> 它是现有体系之上的**增量**：用"像一个真实学生"的方式，登录有头浏览器，从新建项目跑到最终展示，观察项目**整个生命周期**各阶段的表现，并按阶段复测 `问题清单_长期维护.md` 的全部 Q-NNN。
>
> 创建日期：2026-07-30
> 关联文档：`问题清单_长期维护.md`（全 Q 映射源）、`prompts/项目生命周期全程测试Agent_Prompt.md`（执行指令）

## 0. 背景：为什么需要生命周期测试

### 现有测试模式的盲区

现有模式（单点回归 spec + 单元测试 + WS 回归）针对**单个问题 Q-NNN** 验证，缺陷是：

1. **看不到"越聊越卡"这类随轮次累积的问题**。如 Q-023 渲染管线根因（历史消息无 memo，渲染开销随对话轮次单调攀升）——在单点测试里"前几轮"测不出，必须跨十多轮才能暴露。这正是用户反馈"反复修、越来越严重"的根源，而单点测试一直漏掉它。
2. **测不到阶段衔接处的回归**。某阶段修复引入的问题可能在下一阶段才暴露（如 stage_07 教学模式门禁影响后续代码生成），单点 spec 各管一段。
3. **不像人**。真实学生会连续走完一个项目，过程中遇到"跑不下去"的各种卡点；现有测试把这些场景切碎成独立用例，看不到连贯体验。

### 生命周期测试的核心思想

> **让自动化测试本身像一个人**：有 user session、有 project session，从开始一个项目，走到最终展示，记录全生命周期遇到的每个问题、每个卡点、所有 log。必要时切入到不同阶段，针对性复现某个 Q。

四个关键特征：

| 特征 | 含义 |
|------|------|
| **全程连贯** | 一个 user session + 一个 project session 从 stage_01 跑到 stage_08，不切断 |
| **分阶段匹配** | 不同阶段重点复测不同的 Q（脑爆阶段测选项卡、代码阶段测长文截断），见下方"阶段 ↔ Q 映射" |
| **可切入复现** | 跑到某阶段发现问题后，可（a）用 API/工具把项目状态切到任意阶段快速复现单 Q，或（b）开新 session 从该阶段继续复现——两种都支持 |
| **生命体征记录** | 全程记录 CPU/内存、渲染帧率、流式 token 速率、卡顿点、报错，输出"生命体征日志"，用于发现"随轮次累积"类问题 |

## 1. 强制要求（红线）

> 以下为生命周期测试的强制约束，测试 agent 必须逐条遵守。

1.1 **必须有头测试**（`PLAYWRIGHT_HEADED=1` / `--headed`）。生命体征（卡顿、滚动、动画）在有头模式下才能观察。

1.2 **必须登录真实用户**。生命周期测试模拟真实学生，必须通过 `fixtures.ts` 的 `registerUser` + `loginViaUI` 建立真实 user session，**不**用匿名 `/create`。这是与现有 AI 回归 spec（多数匿名）的关键区别。

1.3 **必须跑完整 8 个阶段**。从 stage_01_brainstorm 到 stage_08_evaluate，中间不得为图快而跳过 ask_question 交互（除非复现策略明确要求）。

1.4 **必须对照《问题清单》全 Q 复测**。按"阶段 ↔ Q 映射"，每个阶段结束后逐项核对该阶段映射的 Q，在报告对照表记录结果。

1.5 **必须输出生命体征日志**。测试期间持续采样：内存占用、AI 首字延迟、token 吞吐率、idle 误触发次数、渲染卡顿帧。日志存 `logs/lifecycle/<日期>/`。

1.6 **禁止改产品代码**。测试 agent 只能读产品代码、写测试代码和文档。发现问题改回 🔴 状态并报告，不擅自改产品代码。

1.7 **禁止为通过而造假**。跑不下去的卡点必须如实记录（这是生命周期测试的核心产出），不得绕过。

## 2. 测试用例清单

> 编号沿用 `TC-DLG-xxx` 体系，并加 `@lifecycle` 标签。
> spec 标签：`@ai @lifecycle`（`@ai` 使其仅在 `RUN_AI_E2E=1` 下运行）。
> **设计原则**：生命周期测试承担两大职责——①复测全部已发现问题（每 Q 一个独立用例，可单独跑）；②发现新问题（异常探查器 + 多场景矩阵）。不预设结论，所见即所得。

### 三层结构

生命周期测试 spec（`lifecycle-journey.spec.ts`）分三层，对应两大职责：

| 层 | 职责 | 内容 | 用例 |
|----|------|------|------|
| A 异常探查器（AnomalyExplorer） | 发现新问题 | 全程被动监听 console error/pageerror/5xx/idle误触发/UI冻帧/卡片异常，自动归类记录 | 内置于每个用例 |
| B 每 Q 独立复测 | 复测全部已发现问题 | 每 Q-NNN 一个独立、可单独运行的用例（`-g "Q018"` 跑单个） | TC-DLG-Q001 ~ Q023 |
| C 主线全程 + 多场景矩阵 | 跨阶段/跨场景发现 | 1 条主线全程串联 + 多主题×多模式场景矩阵 | TC-DLG-035、TC-DLG-MATRIX |

## 5. 生命体征与异常探查器记录规范

### 5.1 异常探查器（AnomalyExplorer）—— 发现新问题的核心

spec 内置 `AnomalyExplorer`，全程被动监听并自动归类记录以下异常。**这是"发现新问题"的主要机制**——不预设结论，跑完看探查器捕获了什么：

| 异常类型 | 监听方式 | 含义 / 关联问题 |
|---------|---------|----------------|
| `console_error` | `page.on('console')` type=error | 任何前端报错，可能是新问题 |
| `pageerror` | `page.on('pageerror')` | 未捕获 JS 异常（严重） |
| `network_5xx` | `page.on('response')` status≥500 | 后端崩溃，Q-014/015 类 |
| `network_4xx_unexpected` | status 4xx（排除 401 跳登录） | 非预期权限/路由问题 |
| `idle_timeout` | console 含"空闲超时" | **Q-023 渲染根因核心信号**（正常应为 0） |
| `auto_continue` | console 含"自动续接" | 可能误判卡死触发续接 |
| `continue_button` | `continue-button` testid 可见 | 可能截断/卡死 |
| `ui_freeze` | `page.evaluate` 响应 > 3s | 主线程被阻塞（渲染根因特征） |
| `duplicate_card` | 同屏 question-card > 1 | Q-004 |
| `residual_card` | 不该有卡片时残留 | Q-021 |

**判定原则**：
- 正常全程，`idle_timeout`、`ui_freeze`、`pageerror`、`network_5xx` 应为 **0**。任一 > 0 即需深挖。
- 探查器捕获的所有异常写入报告"发现的问题"章节，作为新问题登记或旧问题复发证据。
- **不要为了通过而绕过**——探查器发现的就是真实问题，如实记录。

### 5.2 生命体征（VitalsRecorder）—— 量化渲染退化

每个用例采样，写入 `logs/lifecycle/<日期>/vitals.json`：

| 指标 | 采集方式 | 告警阈值 |
|------|---------|---------|
| AI 首字延迟 | `Date.now()` 记录发消息到首个 token 到达 | 第 N 轮 / 第 1 轮 > 3x |
| 内存（usedJSHeapSize） | `performance.memory.usedJSHeapSize`（Chromium） | 随轮次单调攀升或峰值 > 初始 250% |
| token 吞吐率 | `streamLogger` token 事件计数 / 耗时 | 持续 < 10 token/s |
| idle_timeout 误触发次数 | 探查器捕获 | > 0（正常对话不应触发） |
| 渲染卡顿 | 探查器 `ui_freeze` | 任何 > 3s 的主线程阻塞 |
| 报错 | 探查器 console_error/pageerror/5xx | 任何阻塞性错误 |
