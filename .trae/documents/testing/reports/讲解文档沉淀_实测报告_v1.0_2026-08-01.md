## 二、测试过程与关键发现

### 2.1 迭代过程（三轮）

| 轮次 | 结果 | 根因分析 |

| 第 2 轮（加循环诱导） | 11 通过 / 2 失败 | 诱导后 AI 回复达 774 字，但保存按钮仍不出现——**根因不是字数** |
| 第 3 轮（复用 stage_07 项目） | **19 通过 / 0 失败** ✅ | 定位到真正根因，见下 |

### 2.2 ⚠️ 关键发现：保存按钮的真实渲染门槛（测试方法教训）

**失败真因不是"AI 回复字数"，而是 `projectId` 为 `local-` 前缀。**

保存按钮渲染条件（Create.tsx:704）：
```js
{projectId && onSaveExplanation && msg.content.length > 200 && (...)}
```
其中 `renderProjectId = projectContext.projectId?.startsWith('local-') ? null : projectContext.projectId`（Create.tsx:3863）。

**前两轮失败的原因**：测试脚本每次新开会话，`sessionStorage.finestem_active_project_id` 为空 → 发消息新建项目 → 前端先用 `local-xxx` 临时 ID → `renderProjectId` 为 null → **即使 AI 回复 774 字，保存按钮也不渲染**（`onSaveExplanation` 被置 undefined）。同时新项目还在早期阶段（stage_01~04），AI 没有代码可讲，回的是项目状态推进说明。

**修复方式**：脚本改为通过 API 查找一个已有代码的 stage_05+ 项目，直接注入 sessionStorage 复用（跳过重新推进 PBL）。复用真实落库项目后 `projectId` 为 UUID（非 local-），保存按钮正常出现。

> **此发现已反映为脚本改进，非产品 bug**——`local-` 项目不显示保存按钮是合理设计（本地未持久化项目无后端讲解文档可写）。但该门槛对自动化测试不友好，建议测试脚本固定复用已落库项目（已实现）。

### 2.3 AI 自动沉淀通路（步骤 9 观察）

日志全程捕获到多次 `[tool_call] artifact_writer` + `[tool_result] artifact_writer ok`，证明：
- AI 走 WS 链路调 artifact_writer 工具通畅
- 提示词规则（zeroclaw_provider.py:60/85）已注入

但本轮 AI 写的多是 dev_log 等工件而非 explanation——符合提示词设计（仅"成体系讲解 >300 字结构化章节"才触发 explanation 沉淀）。手动保存通路（步骤 1~3）已完整验证 explanation 落库，故自动沉淀列为观察项。

## 五、遗留与建议

1. **测试脚本改进（已完成）**：原脚本每次新建项目导致 projectId 为 local-，保存按钮不渲染。已改为优先复用 API 查到的 stage_05+ 项目，注入 sessionStorage。后续维护此脚本时注意此模式。
2. **AI 自动沉淀（步骤 9）依赖模型行为**：本轮观察项已捕获 artifact_writer 工具链路通畅，但 explanation 自动写入需 AI 产出"成体系 >300 字讲解"才触发（提示词设计如此）。若需强制验证自动沉淀，可用后端 `.dbg/verify_explanation_api.py` 的工具 append 断言（已覆盖）。
3. **Demo「我的讲解回顾」（步骤 12）为条件项**：需 MOCK_USER 有从该 Demo fork 且已沉淀讲解的项目。若要强制覆盖，需先手动 fork 一个 Demo 并保存讲解，再跑脚本。
