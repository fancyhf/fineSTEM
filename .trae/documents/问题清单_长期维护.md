### Q-001 选项卡丢失（间歇性）

**状态**：🟡 部分修（tool_call 路径已修，但仍有间歇丢失）

**现象**：AI 调用了 `ask_question` 工具（trace 日志可见），但前端没有渲染出选项卡。约每 3-4 次对话出现 1 次。

**根因分析**：
- ZeroClaw 推送 tool_call 帧和 chunk 帧是异步的
- 如果 tool_call 帧在 done 帧之后到达，或 WebSocket 连接不稳定导致丢帧，前端会错过 ask_question
- 前端 tool_call 处理在 `useStreamingChat.ts` line 598-635，依赖 `data.name === 'ask_question'`（经 normalizeToolName）

**修复记录**：
- 2026-07-22：加了 `normalizeToolName` 处理 `finestem__` 前缀
- 2026-07-22：加了 `questionFired` 标志防止 done 帧重复渲染

**仍需修复**：
- 需要加 tool_call 帧重试/缓存机制，确保 done 帧到达时所有 tool_call 已处理
- 或在 done 帧增加延迟检查（done 后等 500ms 再检查是否有遗漏的 ask_question）

**测试要求**：
- 连续 10 轮对话，统计选项卡丢失率（目标 < 5%）
- WS 抓帧：对比 tool_call 帧数量和前端渲染的卡片数量

### Q-003 markdown fallback 误把总结/状态汇报解析成选项卡

**状态**：🟢 已修（2026-07-27 双重防线彻底修复）

**现象**：AI 回复用 markdown 列表介绍项目功能（如"一个番茄钟专注计时器，包含：- 25分钟倒计时 - 待办任务增删改查..."），前端把这种**功能介绍列表**误解析成让用户选择的选项卡。此外状态汇报/进度总结（如"当前进度：1.选题完成 2.开题进行中"）也会被误识别。这是反复出现的老问题。

**反复出现的根因**：文本 fallback 规则本质是"猜"，单层规则永远在"误识别"和"漏识别"间拉锯——每次收紧规则（Q-011 的 extractChoiceListStrict）会解决眼前 case，但 AI 新的表达方式（番茄钟的"包含："）又会绕过。

**2026-07-27 彻底修复（前端增强 + 后端二次确认双重防线）**：

实测番茄钟 case 确认三个漏洞：
- 纯功能介绍（无问号）：宽松版 `parseQuestionsFromText` 误识别
- 上方含问号（"你想做番茄钟吗？...包含："）：严格版 `extractChoiceListStrict` 误识别（`[?？]` 万能触发）
- 含"想要/哪些"：同样误识别

修复方案：前后端各加一层独立防线，任一层拦截即丢弃。

| 防线 | 位置 | 措施 |
|------|------|------|
| 前端第一防线 | `questionParser.ts` | ① 新增 `isLikelyQuestionTitle`：标题必须是疑问句（去掉裸 `[?？]` 万能触发，要求配合疑问词），且不含列举引导词（包含/包括/功能如下）。② 新增 `isFunctionDescriptionList`：≥50% 选项含技术动作词（倒计时/增删改查/统计...）则拒绝。两个 fallback 共用。 |
| 后端第二防线 | `question_verifier.py` + `POST /chat/verify-question` | 前端文本兜底解析出候选卡片后，调后端做权威二次判断（独立规则，比前端更全）。纯规则无 LLM，<10ms。 |
| 接入 | `questionConfirm.ts` + 4 入口 | 仅文本兜底路径（extractChoiceListStrict / parseQuestionsFromText）调后端确认；ask_question 工具路径（最可信）不确认。失败/超时降级放行（不漏真问题）。 |

**关键设计**：
- 不关闭 fallback（避免 Q-002 漏识别回潮），而是用双重防线把误识别压到最低
- 前端先拦明显的（省 HTTP 往返），后端兜住前端漏判
- 两端规则独立维护，避免单点失效

**验证**：番茄钟 3 个变体场景前后端都正确拒绝；真问题（选轨道/教学模式/年级/兴趣多选/比如）全部保留，无退化。

**2026-07-28 误伤修正（黑名单收紧）**：
- 初版 `LISTING_INTENT_PATTERN` 含"具备/特点/特性"，导致真问题被误杀——项目 `8a7c155e` 中"你想让它**具备**什么核心功能？选一个"被"具备"误命中而拒绝。
- 修正：从黑名单移除"具备/特点/特性"（在正常提问里太常见），只保留明确的列举引导词（包含/功能如下/分为/涵盖等）。前后端同步。
- 验证：番茄钟功能介绍仍被拦截；"具备什么功能"真问题不再误杀；教学模式等不退化。

**重要区分**：AI 回复分两类，正确处理不同——
- **选择题**（"选一个/哪种"）→ 应渲染选项卡，靠工具调用或文本兜底识别
- **开放追问**（"请任选 1-2 个回答/你有什么想法"）→ 不应渲染选项卡，学生用输入框自由回答。这是正常行为，不是 bug。

**测试要求**：
- 见 RT-03 / RT-10：总结文本不误产生卡片
- 见 TC-DLG-028：番茄钟功能介绍不误识别（新增）
- 见 TC-DATA-007：后端 verify-question 接口测试（新增）

### Q-004 同一组问题出现重复选项卡

**状态**：🟢 已修（2026-07-23 加延迟检查）

**现象**：同一张选项卡在屏幕上出现两次。用户点掉一张还有一张。

**根因**（2026-07-23 深入分析）：
- 双路径渲染：tool_call 路径渲染一次（onQuestions），done 帧的兜底又从 AI 文本解析出选项渲染第二次
- `questionFired` 标志本应防止重复，但 **tool_call 帧和 done 帧存在异步乱序**——done 帧到达时 tool_call 帧可能还没到，`questionFired` 仍为 false，导致走了兜底
- 2026-07-23 实证：trace 显示 AI 调了 ask_question（09:21:22），但同一轮 AI 文字里也有选项列表，兜底也提取了一张卡

**修复记录**：
- 2026-07-22：加 `questionFired` 标志，tool_call 已渲染则 done 帧跳过
- 2026-07-23：done 帧收到后**延迟 500ms** 再检查 questionFired——给迟到的 tool_call 帧留窗口，500ms 后仍为 false 才走兜底
- 2026-07-23：收紧 extractChoiceListStrict 意图词，减少误提取概率

**仍需修复**：
- 如果 Q-003 采用方案 A（关闭 fallback），此问题自动消失
- 需验证 session 恢复路径（refresh 页面后 pendingQuestions 恢复）不会重复

**测试要求**：
- 连续 5 轮对话，每轮检查是否有重复卡片
- 刷新页面后检查卡片不重复

### Q-005 AI 反复问已答过的问题

**状态**：🟢 已修（R05 验证通过 2026-07-23）

**现象**：用户已经回答了项目名称，但 AI 在后续轮次再次提问项目名称。或用户已选年级，AI 又问一次年级。R03/R04 测试中 11 轮全部问同一个"年级"问题。

**根因**（两层，R05 最终确认）：
1. **测试代码 bug（主因）**：Playwright 的 `clickFirstOption` 只点了选项按钮，没点"确定"按钮。QuestionCard 设计是"点选项→切换选中，点确定→提交"。只点选项不点确定，`handleQuestionAnswer` 从未被调用，`[选择]` 消息从未发送给 AI。
2. **React 反模式**：`handleQuestionAnswer` 里 `setTimeout(handleSend)` 在 `setPendingQuestions` updater 回调内，React 18 严格模式可能双执行或丢弃副作用。
3. **context 注入不足**：只注入问题标题，没注入具体答案值。

**修复**：
1. 测试代码：`clickFirstOption` 增加 `clickSubmitButton`——点选项后自动点"确定"提交
2. `handleQuestionAnswer`：副作用（`setTimeout(handleSend)`）移出 `setPendingQuestions` updater，在 setState 外面执行
3. `studentProfileRef`：记录 `{title → labels}` 具体答案，注入 `student_profile: 年级=初中; 时间=6小时`
4. system_prompt：加"读完 student_profile 后绝对不要重复问"规则

**R05 验证**（Playwright 有头 TC-DLG-006）：
```
stage_00 轮1: 你现在是哪个年级？
stage_00 轮2: 你这次研学大概有多少时间？
stage_00 轮3: 你对做什么项目有想法了吗？
stage_01 轮1: 你平时课余时间喜欢做什么？（多选）
stage_01 轮2: 你想做哪个游戏项目？
...
```
8 轮全部不同问题，AI 正确推进 ✅

**测试要求**：
- 完成 stage_00（3 轮问答）后，进入 stage_01，验证 AI 不再问年级/时间
- 回答项目名称后，验证 AI 不再问名称
- ⚠️ 测试脚本点击选项后必须点"确定"按钮，否则答案不提交

### Q-007 AI 只总结不给选项，导致流程无法推进

**状态**：🔴 未修

**现象**：AI 回复了一大段项目总结/分析，但没有调用 ask_question 给出下一步选项，也没有明确告诉用户该做什么。用户不知道如何继续。

**根因**：
- AI 倾向于"分析"而非"提问"（尤其 context 变长后）

- system_prompt 加规则："每个阶段回复的结尾必须有明确的下一步——要么调用 ask_question，要么明确告诉学生该做什么"
- 关闭 markdown fallback（解决 Q-003 的同时，避免 AI 误以为总结=选项）

**测试要求**：
- 每轮 AI 回复后，验证有明确的下一步动作（ask_question 或文字指引）
- 验证不会出现"只有总结没有动作"的死循环

### Q-011 AI 文字列选项但不调 ask_question（DeepSeek 模型行为）

**状态**：🟢 已修（2026-07-23）

**现象**：DeepSeek 模型约 10-15% 的轮次会在文字里列选项（如 `- 🌐 Web 应用\n- 🎮 游戏开发`）但**不调用 ask_question 工具**。前端只渲染 tool_call 路径的卡片，这些文字选项无法点击。

**根因分析**（trace 日志实证）：
- 15 轮对话中 2 轮（~13%）AI 没调 ask_question——03:33:07 和 04:58:09
- DeepSeek 的工具调用倾向不如 Claude/GPT 强，多轮对话后 context 变长时更容易退化为文字
- 之前的 markdown fallback（extractQuestionsFromMarkdown）太宽松，把总结文本也解析成卡片（Q-003），被关闭
- 关闭后 Q-002/Q-011 无法兜底

**修复方案**：`extractChoiceListStrict`——极严格的选项列表兜底（`questionParser.ts`）
- **5 个条件全部满足**才提取：
  1. 列表上方紧邻行含选择意图词（`?/？/选/哪个/比如/想要/感兴趣/挑一个`）
  2. 列表项是短词（≤15 字纯文字，去掉 emoji 后）
  3. 列表项不以句号结尾（句号=完整句子=不是选项）
  4. 列表项不以状态标记开头（`✅❌✓✔`）
  5. 列表 2-8 项
- 中文括号 `（description）` 正确拆分为 label + description
- done 帧路径：tool_call → XML → extractChoiceListStrict（仅在前两者都没命中时启用）

**与 Q-003 的关系**：Q-003 是旧 fallback 误识别总结文本。`extractChoiceListStrict` 通过"选择意图标题+短词"双重过滤解决了这个问题——总结的编号列表（`1.基础信息收集 2.项目创建`）上方标题不含选择意图词，不会被提取。

**测试要求**：
- AI 发文字选项列表（无 tool_call）→ 验证前端兜底渲染卡片
- AI 发总结文本 → 验证不误产生卡片
- WS 连续 10 轮 → 统计兜底命中率

### Q-012 编码阶段不提供教学模式选项，直接吐代码

**状态**：🟢 已修（2026-07-23）

**现象**：进入编码阶段（stage_07_execute）后，AI 说"在卡片上选你喜欢的编码方式"但实际没有选项卡（既没有 ask_question tool_call，前端兜底也没识别到）；用户反馈"看不到编码方式"后，AI 不重新提供选项，而是直接吐出代码。这是一个高频问题。

**根因分析**（三层缺陷）：

### Q-016 对话内容不落库，打开项目 AI 对话流空白

**状态**：🟢 已修（2026-07-28 保存时序修复）

**现象**：用户打开"进行中"的项目，AI 对话流和代码都是空的。但项目实际聊过天——PBL 阶段数据（standard_step_data）存在，说明推进过流程。仅对话内容（chat_messages）丢失。

**根因分析**（三层验证确认）：

1. **数据现状**：6 个受影响项目的 `chat_messages=[]`、`chat_saved_at=None`，但 `standard_step_data` 有内容（499-567 字节），证明 PBL 引擎推进过、用户确实聊过。
2. **对比 7-18 备份**：这些项目在备份里就已经是空的——对话**不是被清空，是从未保存成功**。
3. **保存逻辑时序缺陷**（`Create.tsx`）：
   - 对话自动保存在 `useEffect`（依赖 `projectContext.projectId`）里，且受 `restoreAutosaveGuard` 拦截
   - **项目创建是延迟的**——用户开始聊天时 `projectId` 还为空，`if (!projectId) return` 直接拦截，对话不保存
   - `ensureProjectCreated` 只在 **AI 生成代码时** 才创建项目；创建后只保存代码，**不补存对话**
   - 即使 projectId 就绪后，保存靠 3 秒防抖 + messages 变化触发，用户刷新/离开稍快就丢
   - **没有任何页面离开时的强制保存**

**修复方案**（4 个互补措施，`Create.tsx`）：

| 措施 | 位置 | 作用 |
|------|------|------|
| `messagesRef` + `saveChatNow` | 新增 | 提取可靠的保存函数（读 ref 最新值、绕过 guard），供关键节点调用 |
| 项目创建后补存 | `ensureProjectCreated` | 项目创建成功立即 `saveChatNow(id)`，补存此前积累的对话（**核心修复**） |
| 页面离开强制保存 | 新增 useEffect | 监听 `visibilitychange`（切后台/最小化/切标签）+ `pagehide`，触发 `saveChatNow` |
| 流式结束强制保存 | `handleSend` finally | 每轮 AI 回复结束（无论成功失败）都 `setTimeout(saveChatNow, 0)`，最高频可靠时机 |

**关于历史数据**：6 个项目的对话**无法恢复**——从未落库，浏览器 localStorage/IndexedDB 也无残留（前端对话只存内存），7-18 备份里已是空的。PBL 阶段数据还在，但原始对话文本永久丢失。

**测试要求**：
- 新建项目 → 聊几轮（不要生成代码）→ 刷新页面 → 验证对话能恢复（此前会丢）
- 新建项目 → 聊几轮 → 切到其他标签页 → 切回 → 验证对话已保存
