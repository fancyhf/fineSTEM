### Q-001 选项卡丢失（间歇性）

**状态**：🟡 部分修（tool_call 路径已修，但仍有间歇丢失）

**现象**：AI 调用了 `ask_question` 工具（trace 日志可见），但前端没有渲染出选项卡。约每 3-4 次对话出现 1 次。

**根因分析**：
- ZeroClaw 推送 tool_call 帧和 chunk 帧是异步的
- 如果 tool_call 帧在 done 帧之后到达，或 WebSocket 连接不稳定导致丢帧，前端会错过 ask_question
- 前端 tool_call 处理在 `useStreamingChat.ts` line 598-635，依赖 `data.name === 'ask_question'`（经 normalizeToolName）

**修复记录**：
- 2026-07-22：加了 `normalizeToolName` 处理 `finestem__` 前缀
- 2026-07-22：加了 `questionFired` 标志防止 done 帧重复渲染

**仍需修复**：
- 需要加 tool_call 帧重试/缓存机制，确保 done 帧到达时所有 tool_call 已处理
- 或在 done 帧增加延迟检查（done 后等 500ms 再检查是否有遗漏的 ask_question）

**测试要求**：
- 连续 10 轮对话，统计选项卡丢失率（目标 < 5%）
- WS 抓帧：对比 tool_call 帧数量和前端渲染的卡片数量

### Q-003 markdown fallback 误把总结/状态汇报解析成选项卡

**状态**：🟢 已修（2026-07-27 双重防线彻底修复）

**现象**：AI 回复用 markdown 列表介绍项目功能（如"一个番茄钟专注计时器，包含：- 25分钟倒计时 - 待办任务增删改查..."），前端把这种**功能介绍列表**误解析成让用户选择的选项卡。此外状态汇报/进度总结（如"当前进度：1.选题完成 2.开题进行中"）也会被误识别。这是反复出现的老问题。

**反复出现的根因**：文本 fallback 规则本质是"猜"，单层规则永远在"误识别"和"漏识别"间拉锯——每次收紧规则（Q-011 的 extractChoiceListStrict）会解决眼前 case，但 AI 新的表达方式（番茄钟的"包含："）又会绕过。

**2026-07-27 彻底修复（前端增强 + 后端二次确认双重防线）**：

实测番茄钟 case 确认三个漏洞：
- 纯功能介绍（无问号）：宽松版 `parseQuestionsFromText` 误识别
- 上方含问号（"你想做番茄钟吗？...包含："）：严格版 `extractChoiceListStrict` 误识别（`[?？]` 万能触发）
- 含"想要/哪些"：同样误识别

修复方案：前后端各加一层独立防线，任一层拦截即丢弃。

| 防线 | 位置 | 措施 |
|------|------|------|
| 前端第一防线 | `questionParser.ts` | ① 新增 `isLikelyQuestionTitle`：标题必须是疑问句（去掉裸 `[?？]` 万能触发，要求配合疑问词），且不含列举引导词（包含/包括/功能如下）。② 新增 `isFunctionDescriptionList`：≥50% 选项含技术动作词（倒计时/增删改查/统计...）则拒绝。两个 fallback 共用。 |
| 后端第二防线 | `question_verifier.py` + `POST /chat/verify-question` | 前端文本兜底解析出候选卡片后，调后端做权威二次判断（独立规则，比前端更全）。纯规则无 LLM，<10ms。 |
| 接入 | `questionConfirm.ts` + 4 入口 | 仅文本兜底路径（extractChoiceListStrict / parseQuestionsFromText）调后端确认；ask_question 工具路径（最可信）不确认。失败/超时降级放行（不漏真问题）。 |

**关键设计**：
- 不关闭 fallback（避免 Q-002 漏识别回潮），而是用双重防线把误识别压到最低
- 前端先拦明显的（省 HTTP 往返），后端兜住前端漏判
- 两端规则独立维护，避免单点失效

**验证**：番茄钟 3 个变体场景前后端都正确拒绝；真问题（选轨道/教学模式/年级/兴趣多选/比如）全部保留，无退化。

**2026-07-28 误伤修正（黑名单收紧）**：
- 初版 `LISTING_INTENT_PATTERN` 含"具备/特点/特性"，导致真问题被误杀——项目 `8a7c155e` 中"你想让它**具备**什么核心功能？选一个"被"具备"误命中而拒绝。
- 修正：从黑名单移除"具备/特点/特性"（在正常提问里太常见），只保留明确的列举引导词（包含/功能如下/分为/涵盖等）。前后端同步。
- 验证：番茄钟功能介绍仍被拦截；"具备什么功能"真问题不再误杀；教学模式等不退化。

**重要区分**：AI 回复分两类，正确处理不同——
- **选择题**（"选一个/哪种"）→ 应渲染选项卡，靠工具调用或文本兜底识别
- **开放追问**（"请任选 1-2 个回答/你有什么想法"）→ 不应渲染选项卡，学生用输入框自由回答。这是正常行为，不是 bug。

**测试要求**：
- 见 RT-03 / RT-10：总结文本不误产生卡片
- 见 TC-DATA-007：后端 verify-question 接口测试（新增）
- **⚠️ Q-003 由单元测试保障，不做 E2E**：Q-003 的防线是纯解析逻辑（前端 `isLikelyQuestionTitle`/`isFunctionDescriptionList` + 后端 `is_real_question`），用单元测试直接验证函数对各类句式的拒绝/放行即可。**禁止**在 E2E 里硬编码"番茄钟"等具体项目主题——那只是当初发现 bug 的特定样本，每次项目主题都不同，硬编码既测不出 Q-003 本质也无法泛化。更关键：E2E 发"功能介绍"给 AI 时，AI 可能合理地调 ask_question 问方向（正常行为），E2E 无法区分"AI 正常提问"和"前端 fallback 误解析"，会误报 Q-003 复发。

### Q-004 同一组问题出现重复选项卡

**状态**：🟢 已修（2026-07-23 加延迟检查）

**现象**：同一张选项卡在屏幕上出现两次。用户点掉一张还有一张。

**根因**（2026-07-23 深入分析）：
- 双路径渲染：tool_call 路径渲染一次（onQuestions），done 帧的兜底又从 AI 文本解析出选项渲染第二次
- `questionFired` 标志本应防止重复，但 **tool_call 帧和 done 帧存在异步乱序**——done 帧到达时 tool_call 帧可能还没到，`questionFired` 仍为 false，导致走了兜底
- 2026-07-23 实证：trace 显示 AI 调了 ask_question（09:21:22），但同一轮 AI 文字里也有选项列表，兜底也提取了一张卡

**修复记录**：
- 2026-07-22：加 `questionFired` 标志，tool_call 已渲染则 done 帧跳过
- 2026-07-23：done 帧收到后**延迟 500ms** 再检查 questionFired——给迟到的 tool_call 帧留窗口，500ms 后仍为 false 才走兜底
- 2026-07-23：收紧 extractChoiceListStrict 意图词，减少误提取概率

**仍需修复**：
- 如果 Q-003 采用方案 A（关闭 fallback），此问题自动消失
- 需验证 session 恢复路径（refresh 页面后 pendingQuestions 恢复）不会重复

**测试要求**：
- 连续 5 轮对话，每轮检查是否有重复卡片
- 刷新页面后检查卡片不重复

### Q-005 AI 反复问已答过的问题

**状态**：🟢 已修（R05 验证通过 2026-07-23）

**现象**：用户已经回答了项目名称，但 AI 在后续轮次再次提问项目名称。或用户已选年级，AI 又问一次年级。R03/R04 测试中 11 轮全部问同一个"年级"问题。

**根因**（两层，R05 最终确认）：
1. **测试代码 bug（主因）**：Playwright 的 `clickFirstOption` 只点了选项按钮，没点"确定"按钮。QuestionCard 设计是"点选项→切换选中，点确定→提交"。只点选项不点确定，`handleQuestionAnswer` 从未被调用，`[选择]` 消息从未发送给 AI。
2. **React 反模式**：`handleQuestionAnswer` 里 `setTimeout(handleSend)` 在 `setPendingQuestions` updater 回调内，React 18 严格模式可能双执行或丢弃副作用。
3. **context 注入不足**：只注入问题标题，没注入具体答案值。

**现象**：用户打开"进行中"的项目，AI 对话流和代码都是空的。但项目实际聊过天——PBL 阶段数据（standard_step_data）存在，说明推进过流程。仅对话内容（chat_messages）丢失。

**根因分析**（三层验证确认）：

1. **数据现状**：6 个受影响项目的 `chat_messages=[]`、`chat_saved_at=None`，但 `standard_step_data` 有内容（499-567 字节），证明 PBL 引擎推进过、用户确实聊过。
2. **对比 7-18 备份**：这些项目在备份里就已经是空的——对话**不是被清空，是从未保存成功**。
3. **保存逻辑时序缺陷**（`Create.tsx`）：
   - 对话自动保存在 `useEffect`（依赖 `projectContext.projectId`）里，且受 `restoreAutosaveGuard` 拦截
   - **项目创建是延迟的**——用户开始聊天时 `projectId` 还为空，`if (!projectId) return` 直接拦截，对话不保存
   - `ensureProjectCreated` 只在 **AI 生成代码时** 才创建项目；创建后只保存代码，**不补存对话**
   - 即使 projectId 就绪后，保存靠 3 秒防抖 + messages 变化触发，用户刷新/离开稍快就丢
   - **没有任何页面离开时的强制保存**

**修复方案**（4 个互补措施，`Create.tsx`）：

| 措施 | 位置 | 作用 |
|------|------|------|
| `messagesRef` + `saveChatNow` | 新增 | 提取可靠的保存函数（读 ref 最新值、绕过 guard），供关键节点调用 |
| 项目创建后补存 | `ensureProjectCreated` | 项目创建成功立即 `saveChatNow(id)`，补存此前积累的对话（**核心修复**） |
| 页面离开强制保存 | 新增 useEffect | 监听 `visibilitychange`（切后台/最小化/切标签）+ `pagehide`，触发 `saveChatNow` |
| 流式结束强制保存 | `handleSend` finally | 每轮 AI 回复结束（无论成功失败）都 `setTimeout(saveChatNow, 0)`，最高频可靠时机 |

**关于历史数据**：6 个项目的对话**无法恢复**——从未落库，浏览器 localStorage/IndexedDB 也无残留（前端对话只存内存），7-18 备份里已是空的。PBL 阶段数据还在，但原始对话文本永久丢失。

**测试要求**：
- 新建项目 → 聊几轮（不要生成代码）→ 刷新页面 → 验证对话能恢复（此前会丢）
- 新建项目 → 聊几轮 → 切到其他标签页 → 切回 → 验证对话已保存
- 验证 `chat_saved_at` 在对话后有值（不再是 None）

**⚠️ 2026-07-30 二次修复（页面卸载时 fetch 被取消）**：生命周期测试 R2 实证复发——刷新后对话 2→0 / 10→0。根因：之前的"页面离开强制保存"用 `saveChatNow`（普通 `fetch`），但页面卸载（刷新/关闭/跳转）时浏览器会**取消未完成的 fetch**（`TypeError: Failed to fetch`）→ 对话不落库。

修复（`Create.tsx`）：
- 新增 `saveChatBeacon`：用 `fetch(url, { keepalive: true })`（等价 sendBeacon，但支持 Authorization header，sendBeacon 无法带 token 会被 401）。
- `pagehide`（页面卸载）事件改用 `saveChatBeacon`；`visibilitychange`（切标签/最小化，页面未卸载）仍用 `saveChatNow`（普通 fetch 可重试）。
- keepalive body 上限 ~64KB，超长降级普通 fetch（教学场景几十轮足够）。

### Q-018 「修复错误」按钮失效，onclick 文本渲染到屏幕

**状态**：🟢 已修（2026-07-28）

**现象**：运行代码报错时，运行结果弹窗里的「让 AI 修复此错误」按钮点击无反应，并且按钮旁边/下方出现一长串 `onclick="(function(){window.parent.postMessage(...)})()"` 这样的**原始 JS 文本**（正是用户截图所见）。

**根因分析**（`Create.tsx` `buildExecutionResultHtml`，line 679）：

按钮 HTML 写成内联属性：
```html
<button onclick="(function(){window.parent.postMessage({type:'code-error',msg:<JSON>},'*');...})()">
```
其中 `msg` 的值是 `JSON.stringify(result.error)`。`JSON.stringify` 生成的 JS 字符串**含双引号 `"`**（如 `"name 'x' is not defined"`）。当这段字符串嵌入到**用双引号包裹的 HTML 属性** `onclick="..."` 时，里面的 `"` 会**提前闭合属性**，浏览器把后续 JS 当成元素后的可见文本渲染——按钮的 onclick 失效，JS 文本泄漏到屏幕。

已用 Node REPL 复现：即使错误只含一个引号（如 `NameError: name "x" is not defined`）就会破坏属性解析。

**对比**：同一文件 `buildHtmlFromCode`（line 623-634）用的是**正确写法**——`innerHTML` 写无 onclick 的按钮骨架 + `setTimeout(0)` 里用 `btn.onclick = function(){...}` 赋值，完全避开属性引号问题。

**修复方案**（`Create.tsx` `buildExecutionResultHtml`）：

把内联 `onclick="..."` 改成与 `buildHtmlFromCode` 一致的「按钮骨架 + script 内 btn.onclick 赋值」写法：
1. 按钮去掉 `onclick` 属性，只保留骨架（无 JS）
2. 在返回 HTML 末尾追加一个 `<script>`，`getElementById('__ask_ai_btn')` 后用 `btn.onclick = function(){...}` 绑定
3. 错误信息通过局部变量 `var errMsg = ${JSON.stringify(JSON.stringify(result.error))}` 传入——双重 stringify 确保即使是含引号/换行/反斜杠的错误串也是合法的 JS 字符串字面量

**验证**（Node REPL）：含 `"`、`\n`、`'`、`\` 的复杂 traceback 作为 `errMsg` 赋值能被 `new Function()` 正确解析，无语法错误。

**测试要求**：
- 见 RT-18：「修复错误」按钮可点击、无文本泄漏
- 运行一段必报错的代码（如 `print(x)` 引用未定义变量）→ 看运行结果弹窗 → ① 屏幕无 `onclick=(function(){...})` 文本 ② 点「让 AI 修复此错误」→ 聊天框自动发出"我的代码运行出错了…请帮我修复"
- 错误信息含双引号（如 `name "x" is not defined`）也必须正常工作（此前正是引号触发 bug）

### Q-019 生成代码后编辑器空白、无代码文件

**状态**：🟢 已修（2026-07-28，前后端双修）

**现象**：AI 明确调用了 `project_code_writer` 工具写代码（AI 文本说"已生成代码"、DB workspace 里代码也存在），但前端编辑器始终空白，左侧"代码文件"区也空（或显示硬编码 `main.py`）。用户看到"已生成代码"的叙述却看不到任何代码，是高频顽固 bug。

**根因分析**（前后端事件断裂，三处缺陷）：

1. **后端 tool 返回缺字段**（`tools.py` `ProjectCodeWriterTool.execute` line 917-923）：`ToolResult.data` 只返回 `{project_id, language, filename, saved_at, code_length}`，**不含 `code` 和 `files`**。
2. **后端有正确事件但前端不收**（`orchestrator.py` line 1008-1023）：后端在 tool 成功后**专门 yield 了一个 `code_generated` 事件**，从 DB workspace 读取完整 `code/files`——数据是对的、最权威的。
3. **前端致命缺陷**（`useStreamingChat.ts`）：`onCodeGenerated` 只在两处触发——
   - `tool_call`/`tool_result` 事件里读 `out.code`/`out.files`（后端 tool 没返回这俩字段 → 永远 undefined）
   - 文本兜底提取
   - **完全没有 `type === 'code_generated'` 的处理分支**！后端精心构造的权威事件被前端整体忽略。

**结论**：工具路径下，后端 `code_generated` 事件带正确数据但前端不接收；前端唯一会读的 tool_call 数据又缺 `code/files`。两端断裂 → 编辑器永远空白，`ProjectFilesPanel` 因 `files=[]` 显示硬编码 `main.py` 或空。

**修复方案**（前后端双保险）：

| 层 | 位置 | 措施 |
|----|------|------|
| 前端主修 | `useStreamingChat.ts` | 新增 `if (type === 'code_generated')` 分支：读后端权威的 `code/files/filename/project_id`，调 `events?.onCodeGenerated?.({...})`。复用 `codeEventFired` 防与文本兜底重复触发。 |
| 后端兜底 | `tools.py` `ProjectCodeWriterTool` | `ToolResult.data` 补 `code` 和 `files`（从入参 `code` 和已构造的 `updated_files` 取），让 tool_result 路径也能自洽（即使 code_generated 事件丢失也有兜底）。 |

**设计说明**：后端 `code_generated` 事件是权威路径（从 DB 读，数据最全最准）；前端新分支是主修复。后端 tool data 补字段是双保险——任一路径断裂都能让代码落编辑器。

**验证**：
- 前端 `tsc --noEmit` 零错误
- 前端 vitest 90 测试全过
- 后端 `ProjectCodeWriterTool` 返回现在含 `code`/`files`（手动核对 data dict）

**测试要求**：
- 见 RT-19：生成代码后编辑器有代码、文件区有文件
- 走到编码阶段（stage_05/07/08）→ AI 调 project_code_writer → ① 编辑器立即显示代码 ② 左侧"代码文件"区显示真实文件名（如 index.html），非硬编码 main.py ③ DB workspace 有代码（已有）

### Q-038 创建页四大疾病：纯问答强建项、发消息卡死、场景提示词未接入、回答落入思考区

**状态**：🟢 已修（2026-07-31）

**现象**（用户报告，附 4 张截图）：
1. 点「问问题」或直接录入“我想问一个 STEM 相关的问题”→ 系统自动创建项目并跳到「2.脑暴选题」，纯提问被强拉进 PBL 九步流程。
2. 发消息后 AI 无任何反馈，卡死在对话框，重新写入也无反应（输入框 disabled + 守卫静默拦截）。
3. 随意问模式下 AI 在「深度思考」折叠区里写了对问题的完整回答，正文只展示一句引导语+选项卡，学生看不到答案。

**根因链**：
1. **强建项**：Q-024 修复时「登录用户无项目就无条件 API 建项」（Create.tsx）+ 流末关键词兜底建项，完全不看场景；后端虽有 SCENE_SYSTEM_PROMPTS 四场景差异化提示词，但只在 REST 编排链路生效——前端主聊天是 WS 直连 daemon，daemon 只读 config.toml 内嵌的 PBL 导向 system_prompt（Q-029 同源问题的场景变体）。
2. **卡死双根因**：① useStreamingChat 的 ws.onclose 只清计时器不 settle promise，握手失败/中途断开时 stream() 永久挂起 → isLoading 永久 true → 输入框永久 disabled；② Create.tsx 的 finally 只复位 isLoading state 不复位 isLoadingRef，异常路径下 ref 残留 true，handleSend 守卫永久静默拦截；另无任何中止手段，用户只能刷新。
3. **回答落思考区**：daemon 的 PBL 提示词驱使 AI 把“回答内容”当作内部推理写进 thinking 帧，正文只留引导+ask_question；提示词从未告知 AI“思考过程学生不可见”。

## 维护规则

1. **发现新问题时**：在此文档添加新条目（Q-NNN），状态设为 🔴未修
2. **修复问题时**：更新状态为 🟢已修，记录修复日期和方案
3. **每次代码改动后**：跑回归测试检查清单（RT-01 ~ RT-39），在测试报告中记录每项结果
4. **测试 agent 必读**：测试 agent 执行测试前必须读本清单，确保覆盖所有场景
5. **问题复发时**：状态改回 🔴，在"最后确认"列更新日期，分析为何复发
6. **HTML 属性禁止内联 JS（Q-018 教训）**：动态生成的 HTML 里，按钮事件一律用 `btn.onclick = function(){...}`（script 内赋值）绑定，**绝不**写进 `onclick="..."` 内联属性——任何含双引号的字符串（如 `JSON.stringify` 结果）都会提前闭合属性，导致 JS 串到屏幕上当文本渲染。
7. **前后端事件契约必须同步（Q-019 教训）**：后端 orchestrator 每新增一种 `yield ("event_type", ...)` 事件，前端 `useStreamingChat.ts` 必须同步新增对应的 `type === 'event_type'` 处理分支。后端发了事件但前端不处理 = 等于没发。建议：后端新增事件时，同时在本清单登记，并在 PR 描述里点名对应的前端处理点。
8. **意图词前后端同步（Q-020 教训）**：前端 `questionParser.ts` 与后端 `question_verifier.py` 的 `QUESTION_TITLE_PATTERN` / `LISTING_INTENT_PATTERN` 必须保持一致——任一端新增识别词，另一端必须同步，否则会出现"前端放行、后端二次确认拒绝"（或反之）导致卡片最终不渲染。
9. **派生数据须与源数据同步（Q-022 教训）**：当同一概念有两份存储（如 `projects.name` 创建默认值 vs `skill_state` 里 AI 确认值），AI 修改源数据后必须同步派生数据。推荐后端在读取入口（如 `_build_workspace_payload`）做"数据自愈"——检测不一致即写回，而非依赖前端记得调更新 API。
10. **流式渲染禁用"每 chunk 全量重渲染"（Q-023 渲染管线教训）**：流式输出回调里，任何 O(n) 清洗（如全文正则）+ setMessages 都必须节流（`requestAnimationFrame`，每帧最多一次），历史消息渲染必须 `React.memo` 隔离。裸"每 chunk 同步重渲染"会随对话轮次累积变卡，进而触发 idleTimer 误判 → 自动续接 → 更卡，是"反复修越来越严重"的典型根因。新增流式回调时务必复用节流机制，不要回到同步渲染。
11. **超时判定须基于真实数据到达，非回调执行（Q-023 idleTimer 教训）**：WS/流式的空闲超时计时器，重置点应在 `onmessage` 最开头（帧一到达即记录时间戳），而非业务逻辑分支内。否则渲染积压时回调迟迟不跑，会误判"卡死"触发续接，放大问题。
12. **新增问题须映射到生命周期阶段**：登记新 Q-NNN 时，在上方"全 Q-NNN 到 PBL 生命周期阶段映射"表中标注它最易在哪个 stage 暴露，供生命周期测试模式分阶段复测。
13. **WS 返回的 project_id 不可无条件覆盖用户拥有的项目（Q-024 教训）**：WS 的 project_creator 工具可能用错误 author_id 创建项目（项目不属于当前用户 → autosave 403）。前端必须：① context 注入 author_id 让 AI 用对；② 用 apiOwnedProjectId 标记用户拥有的项目，WS 的 project_id 只在无项目时才采用。任何"用 WS 的 ID 覆盖前端已有 ID"的逻辑都要先校验归属。
14. **autosave 403 是高危信号（Q-024 教训）**：测试中 console 出现 `[autosave:*] 保存失败: 无权操作此项目`即项目归属错乱，会导致刷新后对话/代码/画像全丢。生命周期测试必须全程监控 autosave 是否 403。
15. **payload 字段必须端到端连通（Q-025 教训）**：凡是在调用方构造、通过 payload 传递的数据（如 `messages` 对话历史），接收方 hook 必须真正读取并发送。Q-025 中 `Create.tsx` 构造了 historyMessages 传进 `stream(payload)`，但 hook 从未读 `payload.messages`——数据构造了却扔掉，AI 因此失忆。新增 payload 字段时，必须验证接收方有对应消费点。
16. **绝对超时须随活动重置，否则误杀长任务（Q-023 totalTimeout 教训）**：流式 totalTimeout 不能从握手后一次性计时而不随 chunk 重置——大段代码生成（多工具+长文本）整体超 120s 会被强制截断。totalTimeout 应像 idleTimer 一样随非终态帧重置，变成"无活动才超时"；idleTimer(短)管"真卡死"，totalTimeout(长,随活动重置)管"永久挂起"，职责分离。
17. **AI 可写通道必须触及前端读取的数据源（Q-026/Q-027 教训）**：前端展示读哪个字段（projects.name、step8.payload），AI 的写入工具就必须能直接或间接同步到那个字段，否则 AI "改了但界面不变"——用户再三催促也无效，体验性灾难。新增前端展示字段时，必须盘点"AI 能不能改到它"；新增 AI 工具时，必须盘点"它写的东西前端读不读"。
18. **水合/合并逻辑不得反向覆盖新数据（Q-027 教训）**：读取入口的“数据自愈/水合回写”（如 GET /workspace 的 stage8 水合）只能补空、不能用旧数据的渲染稿覆盖工具刚写的新内容。双向同步必须区分触发方（表单保存 vs 工具写入 vs 读取水合），用参数（如 `sync_evaluate_content`）显式声明方向，否则形成“写入→回滚”死循环。
19. **AI 行为规则必须写对载体（Q-029 教训）**：fineSTEM 有两条 AI 链路，system prompt 来源不同：① 前端聊天 WS 直连 daemon（主链路）→ 规则在 `H:\dev-env\zeroclaw\config\config.toml` 的 `system_prompt`，改完必须重启 daemon；② 后端 orchestrator REST 流式 → 规则在 `.trae/skills/stem-pbl-guide/SKILL.md`，skill_loader 按内容 hash 热加载、改完即生效。给 AI 加规则前先确认目标链路，两条链路都要生效就两头都写；写错载体等于没写，且会误判“修复无效”。
20. **占位/默认文案不得占据水合最高优先级（Q-037 教训）**：当某字段有「系统生成的占位默认值」与「用户/AI 写入的真实值」两个来源，水合/回填逻辑绝不能让占位值优先级最高——否则占位一旦种入就永久固化，真实内容永远无法替换（评估展示残留模板的根因）。正确做法：占位值降为最低兜底（先清空让真实来源填充，无真实来源时才还原占位）。同时，凡是「从工件正文解析结构化字段」的解析器，必须能容忍未知子标题（按标题层级处理，深层未知标题归为章节内容而非截断章节），否则真实文档解析为空会让联动静默失效。
