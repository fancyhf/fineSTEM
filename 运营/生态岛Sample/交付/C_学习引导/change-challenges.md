# 改造挑战（change-challenges）

- 适用：eco-island-v1（冻结）。改造会改变模型行为 → 按公共约定 §8，**标准改造完成后你的 modelVersion 应标为 `eco-island-v2`（自己起的名+v2）**，并在《07-变更记录》写明改了什么、怎么验证。
- 起点：`my-island.html`（你修完 5 个 TODO 的版本，见任务卡 4–9）。**不要在 reference 或 starter 原件上改**。
- 通用验收原则（每一级挑战都适用）：
  1. **先预测、后运行**：跑之前写下你预期的第 60 步或关键事件。
  2. **同起点对比**：改造前后用完全相同的开局和除目标外完全相同的设置。
  3. **最小用例验收**：用一两个"一步就能区分对错"的用例验收，不能只看"界面没报错"。
- 证据标注：本文标【A 实测】= A 包 test-cases.json / A-E002；【B 实测】= B 包 variants/standard/notes.md；【C 实测】= 本包 walkthrough 期间 node 实测（证据 C-E001，脚本与结果存 G:/tempcache/c-pkg/scripts/，明细见 walkthrough-report.md）。凡未标注的数字，你运行后自己填。

## 挑战 L1（入门）：参数比较——改条件，不改规则

入门挑战只动滑杆和下拉框，一行代码都不改。目标是练"改变一个条件"的完整对照流程。

### L1-a 初始动物 5 / 20 / 40 三连跑

- **操作**：从 `my-island.html`（或 reference）出发，三局全部用默认草 60/水 50/中雨，只改初始动物滑杆为 5、20、40，各跑 60 步，记录：动物首次归零步、动物是否迁回、第 60 步三数。
- **预测再验证**：先猜哪局动物活得最久、哪局最惨。很多人猜"动物越多越旺"——跑完再回答。
- **已知锚点**（可直接对照你的运行结果）：
  - 动物 20（默认）：第 9 步归零、第 34 步迁回、第 60 步 20.8/4/100【A 实测 TC09】
  - 动物 40：第 10 步水见底、第 15 步归零、第 60 步仍 0【A 实测 A-E002 S-D】
  - 动物 5：**A/B 未实测，预测并验证**。C 包实测供对照：第 11 步首次归零、第 60 步 22.4/1/100【C 实测 C-E001】
- **思考题**：40 只更快渴死水（每步 0.3×40=12 > 中雨 +3），5 只也没能避免灭绝——**在这个参数范围里，"灭绝"和初始数量关系不大**。为什么？（提示：吃草速度 0.8×只数 与草生长上限 +2 的对比，只在只数很小时才翻转；算算动物 2 时一步吃多少。）

### L1-b 下雨档位三连跑

- **操作**：默认开局不变，只改下雨档位（小雨/中雨/大雨）各跑 60 步。
- **已知锚点**：三档的动物都在**第 9 步归零、第 34 步迁回**——崩溃时点完全相同；只有水位不同（第 60 步水 44.3 / 100 / 100）【A 实测 A-E002 S-A/S-B/S-C】。
- **记录**：三行表 + 一句话结论（"雨档改变了什么、没改变什么"）。
- **衔接知识**：这是知识第 3 章"最短板"的实验版——补非短板，无效。

### L1-c（自选加餐）：找一组"动物永不灭绝"的参数

- **任务定义**：只调三个滑杆和雨档，找到一组参数：60 步内动物**从未**归零（全程最低 > 0）。写下参数、预测原因、给出 60 步全程的动物最低值。
- **难度提示（级 1）**：默认参数和更大动物都不行（L1-a 已证明）。往"更小的动物"方向想。
- **实测事实供对照**（C 实测 C-E001，中雨、水 50）：确实存在这样的组合，例如**初始草 30 / 动物 2 → 第 60 步 39.6/4/100，全程动物从未归零**；初始草 40/动物 4、初始草 50/动物 2 也成立。而初始动物 ≥6 的所有测试组合都至少归零一次。
- **思考**：为什么"小种群 + 中低草"反而稳？（提示：2 只动物一步吃 1.6 < 草生长 +2——吃不过来长；草停在 20–50 区间，动物不多不少。这不是"生态健康"，只是这个规则下的一种平衡——说"稳"要说清定义。）

**L1 保存什么**：两张三行对照表 + L1-c 的参数记录 → D 模板《06-配置与测试》；结论句 → 《05-开发与调试》。

## 挑战 L2（标准改造）：干旱岛——新增"无雨"档

这是任务书要求的"一项能比较原版与修改版的规则改造"。B 包已有一份参考实现（`variants/standard/`）——**先自己做，卡住或做完后再看它**。

### 2.1 改造目标

新增第四个雨档"🌵 无雨（每步 +0）"：水只出不进。其余四步规则**一字不动**。

### 2.2 预期现象（先写预测）

【B 实测】干旱岛（low=0，默认开局 60/20/50）60 步走势：第 1 步水 44（+0−6）；第 9 步动物归零；第 10–30 步水冻结在 14.9（没动物喝水也没雨补）；第 40 步草>50 动物短暂回 4；第 47 步 4 只动物喝干最后一口水 → 干旱，草停止生长；**第 60 步 = 草 16.4 / 动物 0 / 水 0**。

对照默认档（20.8/4/100）：没有雨，连"水满后躺赢"的结局都没有了。先把你预测的 60 步终态写下来，跑完对照。

### 2.3 操作步骤

1. 复制 `my-island.html` 为 `my-drought.html`。搜索 `REPLENISH`（或档位表 `{ low: 1, mid: 3, high: 6 }`），把 `low: 1` 改成 `low: 0`。
2. 搜索 `repSel`（下雨下拉框），给"小雨"选项的文案改成"🌵 无雨（每步 +0）"（或新增一个 `<option value="low">`，保持 value 不变最简单）。
3. 把 `MODEL_VERSION` 改成 `"eco-island-v2-drought"`（你改了模型规则，必须换版本标签——公共约定 §8）。
4. 保存、运行，跑完 60 步对照 §2.2 的锚点。

### 2.4 必教知识点：`||` vs `??`——改造"不生效"的最大坑

看你的档位那一行行尾的兜底写法。**如果你（或 AI）写的是 `|| 3`，改造会静默失效**：

```js
// 陷阱版（B 包实际踩过这个坑）：
const replenishSpeed = { low: 0, mid: 3, high: 6 }[environment.replenishLevel] || 3;
// JS 里 0 是"假值"！low 档取到 0 之后，0 || 3 会算出 3 —— "无雨"静默变成"中雨"！
// 界面显示"无雨"，行为却是 +3，而且没有任何报错。

// 正确版（B 包 variants/standard 采用，starter 也已用）：
const replenishSpeed = { low: 0, mid: 3, high: 6 }[environment.replenishLevel] ?? 3;
// ?? 只在左边是 null/undefined（档位名写错）时才兜底；0 是有效值，原样通过。
```

为什么这是最好的编程课之一：

- 症状具有欺骗性：程序不报错、界面正常、动物照常崩溃——你很容易以为"改了没用"其实是"改了被覆盖"。
- A 包在预演中真实踩过这个坑（第一次跑结果与中雨完全相同）；B 包在实装干旱岛时又踩了一次并记录在 variants/standard/notes.md。
- **最小验收用例**就是为了抓这种错误而生（见 2.5 的 V2-2：全零开局 + 无雨档，一步就能区分 0 和 3）。

### 2.5 改造验收（先跑这三个用例，再谈"改造完成"）

| 用例 | 输入 | 正确结果 | 抓什么错 |
|---|---|---|---|
| V2-1 | 默认开局（60/20/50）+ 无雨档，走 1 步 | 草 46 / 动物 20 / **水 44**（=50+0−6；A 给的手算预期） | 对照默认档 TC01 的水 47：只差水的 +3 → 证明 low=0 生效 |
| V2-2 | 全零开局（0/0/0）+ 无雨档，走 1 步 | 草 0 / 动物 0 / **水 0** | **抓 `||` 陷阱的最小用例**：若水=3，你的 0 被 `||` 兜底成了 3（对照：小雨档此用例水=1【A 实测 TC06】） |
| V2-3 | 默认开局 + 无雨档跑 60 步 | 草 16.4 / 动物 0 / 水 0 附近【B 实测】 | 长链回归；C 包复现一致【C 实测 C-E003】 |

再加一条防退化检查：改完后把原三个档位各跑一遍默认局，第 60 步应仍是 20.8/4/100（中雨）、44.3/…/100 相关锚点不变——**确认你没改坏冻结行为**。

### 2.6 完成后

- 记录《07-变更记录》：改了什么（2 处）、为什么、影响（贴 V2-1/2/3 结果 + 60 步前后对比表）、`||` vs `??` 你踩没踩坑。
- 回答干旱岛引导问题（B 包 notes.md 原题）："为什么无雨岛的动物第一次灭绝后，草反而恢复了？回来的 4 只动物又做了什么？"

## 挑战 L3（进阶，只给思路）：改规则本身

进阶挑战改 `stepModel` 内部的规则。改前想清楚：这是新模型了，以前所有实测锚点全部作废，要重新测。

### L3-a 食草系数可调

思路：把 `const eaten = herbivores * 0.8;` 的 0.8 提为配置 `config.grazingRate`，界面加滑杆（建议 0.4–1.2）。

【A 预演 + C 实测 C-E001 复核一致】默认开局、中雨、60 步终态：

| 系数 | 首次归零步 | 第 60 步 |
|---|---|---|
| 0.5 | 12 | 22 / 2 / 100（动物尚存） |
| 0.6 | 11 | 21.4 / 0 / 100 |
| 1.0（原值） | 9 | 31 / 0 / 100 |
| 1.2 | 8 | 42.8 / 0 / 100 |

**读数陷阱（A 特别提醒，必看）**：系数越大，第 60 步草反而越高（1.2 → 42.8）——因为动物死得早、后期没人吃草。**第 60 步只是循环中的一个切片，不是"系数越大草越多"的单调规律**。实装后先跑多组再写任何结论；引用"第 60 步"必须带窗口意识。

### L3-b 拯救动物挑战（结合 L1-c）

任务：让默认开局（60/20/50）的动物"活得好"。先定义"活得好"（60 步末 >0？全程 >0？种群 ≥ 初始值？），再分别试：

1. 只调初始条件（L1-c 已知：小种群+中草可全程 >0，但那改变了开局——算"拯救"吗？）
2. 只调雨档（已知无效——最短板）
3. 改食草系数（L3-a：0.5 时 60 步末动物尚存，但**中途仍会在第 12 步归零一次**【C 实测】——你的"活"的定义现在重要了）

这个挑战的产出不是"找到答案"，而是**一份带定义、带对比、带边界句的实验记录**。

### L3-c 更多思路（不展开）

繁殖规则改成渐进式（不再阈值跳变）；给草加养分循环；给天气加骰子（注意：一加随机，同输入不再同输出，确定性声明作废，所有锚点失效——想想值不值）。

## 改造路线小结

```
L1 参数比较（不改码） → L2 干旱岛（改 2 处 + ?? 知识点 + 最小用例验收）
                     → L3 食草系数/拯救动物（改规则 = 新版本 = 全链重测）
```

每一步的《07-变更记录》都要能回答：改了什么 / 为什么 / 影响如何验证 / 有没有改坏别处。
