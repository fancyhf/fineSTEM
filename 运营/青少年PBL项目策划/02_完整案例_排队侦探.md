# 完整 PBL 案例：排队侦探

> V1历史案例：保留为算法与模型比较练习；当前主方向见[V3线上自助Sample体系](07_V3_线上自助Sample体系.md)。

副标题：同样两个窗口，两条队伍和一条共享队伍，怎样让大家少等一会儿？

日期：2026-10-19｜状态：教学设计与试课准备稿，尚无真实学生试做结果。

## 1. 项目卡

| 项目 | 设计 |
|---|---|
| 项目编号 | P01 |
| 对象 | 12–15 岁，零基础至初级；独立或两人一组 |
| 情境 | 饭堂打饭、图书借还、展览签到等熟悉的服务场景，由学生选一个 |
| 驱动问题 | 同样两个服务窗口，不同排队规则会怎样改变等待时间？有没有一样快的情形？ |
| 主领域 | 服务工程与运筹思维；数学统计；计算机模拟 |
| 学科知识 | 到达/服务/等待的区别；平均值和最大值；比较时保持哪些条件一致 |
| 主代码路线 | HTML/CSS + JavaScript，浏览器网页 |
| 最小作品 | 输入一组到达/服务数据，运行两种规则，列出每人等待及汇总指标 |
| 标准工时 | 6 次活动×60分钟，另留观察、整理与短文撰写合计1–2小时，可分两个周末或六次课 |
| 必备材料 | 可使用 fineSTEM 的电脑、纸笔；用积木或纸片模拟排队即可 |
| 可选材料 | 秒表；获允许的非识别性现场计时。现场观察不是开课前提 |
| 最终观众 | 家长、另一组学生或受邀教师 |
| 学生决策 | 选择场景、确定优先指标、提出第三种规则或新测试情景 |

孩子最后应能说清：“我比较了什么；怎样保证比较有意义；我改过哪段代码；什么证据支持我的判断；还有什么不能确定。”

## 2. 可直接使用的开题示范

以下是教师提供的开题样例，学生必须改写场景、假设和关注指标。假设不是结论。

> **题目**：两个窗口怎样排队，等待时间会更短？
>
> **问题来源**：我发现有时一队走得快，另一队一直不动。我想知道，同样两个窗口，如果所有人排同一条队，有空窗口就过去，会发生什么。
>
> **我的初始猜想**：服务时间有长有短时，共享队伍可能减少等待；每个人服务时间一样时，两种方法可能一样。
>
> **我要比较的办法**：A 为到达后按编号交替分到两个固定队伍，分队后不换队；B 为按到达顺序排共享队伍，到最早空出的窗口办理。
>
> **保持相同**：人数、到达时刻、每个人的服务时长、两个窗口、并列处理规则。
>
> **衡量办法**：平均等待、最长等待、全部人完成的时刻；我还会看看是否有人特别吃亏。
>
> **最小作品**：能比较两种策略的网页，有逐人表格和清楚标注的单位。
>
> **成功标准**：通过事先手算的测试；完整记录四个情景；让另一组用同样输入复现一个结果；能解释一处代码修改。
>
> **暂不考虑**：插队、半途离开、走向窗口需要的时间、窗口办理能力不同。现实中的队伍可能存在这些情况，所以我的结果只适用于设定模型。

## 3. 模型定义：先说清规则再写代码

### 3.1 每个值的含义

| 字段 | 含义 | 单位/约束 |
|---|---|---|
| `id` | 客人匿名编号 | 唯一，不记录姓名 |
| `arrival` | 从计时起点到客人到达的时间 | 秒，有限数值，≥0 |
| `service` | 该客人占用窗口的时间 | 秒，有限数值，>0 |
| `start` | 开始接受服务的时刻 | 秒 |
| `finish` | 完成服务的时刻 | 秒 |
| `wait` | 排队等待的时长 | `start - arrival`，秒 |
| `available[j]` | j 窗口最早再次可用的时刻 | 秒，初始为0 |

将客人按到达时间升序排序；到达相同按原始编号升序。服务时长跟随客人，在两个窗口都相同。窗口之间没有优先差别。输入不能在一种策略里被改写后再交给另一种。

### 3.2 两个被比较的策略

**A：两条固定队伍，交替分配。** 排序后第0、2、4…号进入窗口0队伍，第1、3、5…号进入窗口1队伍；各队按进入次序服务，中途不换队。这是明确的教学分配规则，不代表现实中所有“两条队”的行为。

**B：一条共享队伍。** 按排序后顺序逐人处理，分配到 `available` 最小的窗口；同样空闲时选择编号较小的窗口。因为采用先到先服务，后到的人不能抢在队伍前面。

选定窗口后，两者使用相同的计算：

```text
start  = max(arrival, available[window])
finish = start + service
wait   = start - arrival
available[window] = finish
```

标准版不必每秒刷新全部人：直接计算下一次开始/完成服务的事件，即可完成本次研究。动画作为讲解层使用，不能成为计算依据。

### 3.3 为什么先保持窗口数一致

一个窗口和两个窗口的比较可以帮助理解排队，但它同时改变了资源量。主实验固定为两个窗口，才能集中讨论排队规则。若增加窗口，则另起“资源投入”实验，报告中写清额外投入，不把它当成规则本身的效果。

## 4. 先手算一个可核对的小例子

**以下四名客人的数据为教学合成数据，不是现场记录。** 全部在第0秒到达，服务时长依次为60、10、10、10秒。

| 客人 | 到达 | 服务 | A窗口 | A开始 | A等待 | A完成 | B窗口 | B开始 | B等待 | B完成 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 | 0 | 60 | 0 | 0 | 0 | 60 | 0 | 0 | 0 | 60 |
| 1 | 0 | 10 | 1 | 0 | 0 | 10 | 1 | 0 | 0 | 10 |
| 2 | 0 | 10 | 0 | 60 | 60 | 70 | 1 | 10 | 10 | 20 |
| 3 | 0 | 10 | 1 | 10 | 10 | 20 | 1 | 20 | 20 | 30 |

| 指标 | A固定分队 | B共享队伍 |
|---|---:|---:|
| 平均等待 | 17.5秒 | 7.5秒 |
| 最长等待 | 60秒 | 20秒 |
| 最后一人完成时刻 | 70秒 | 60秒 |

这里“最后一人”指最后完成的人，取所有 `finish` 的最大值。完成时刻与平均等待不是同一个指标。本例只能说明这组输入下两种规则不同，不能据此推断所有现实队伍。

还可以发现：客人3在B中反而等待更久。这让孩子讨论“整体平均更好”是否等于“每个人都更好”。

## 5. 六次活动脚本

| 次数与阶段 | 60分钟安排 | 讲什么知识 | 孩子写/改什么 | 当次留下什么 |
|---|---|---|---|---|
| 1：初始化→脑爆→开题 | 现象10分，纸片模拟15分，问题与假设20分，开题卡15分 | 到达、服务、等待；问题与结论的区别 | 暂不要求代码，画出四人的服务顺序 | E01问题来源、E02开题与假设 |
| 2：范围→技术→设计→计划 | 范围10分，选路线10分，手算20分，画数据流与拆任务20分 | 公平比较、单位、输入输出 | 写伪代码和函数职责；设计阶段允许骨架，分步计划阶段只写任务 | E03模型假设、E04手算、E05设计与任务表 |
| 3：编码实现一 | 回顾10分，单窗口函数20分，结果表15分，边界测试10分，记录5分 | `max`、循环、状态、函数 | 完成单窗口计算和汇总；解释每次循环变化 | E06 v0.1代码、E07测试与调试 |
| 4：编码实现二 | 预测10分，两窗口策略20分，对照手算15分，同伴检查10分，记录5分 | 数组索引、策略分离、共享计算 | 完成A/B窗口选择；使表格与指标对应 | E08 v0.2代码、E09四人例对照表 |
| 5：比较实验 | 冻结协议10分，四情景运行25分，结果解释15分，异常与局限10分 | 控制变量、指标、反例；进阶才引入重复随机试验 | 批量跑固定数据并导出/抄录结果；选择一项有理由的修订 | E10实验输入与输出、E11修订记录 |
| 6：验收展示 | 整理证据10分，讲解与提问20分，针对反馈补测15分，修改结论与短文提纲15分 | 结论与证据对应，模型边界 | 复现一组数据；完成最后一次改动并说明 | E12反馈/补测、E13研究短文与讲解 |

观察与成文的1–2小时在六次活动间完成，或拆为额外支持课，不能把它隐含进第6次的60分钟。零基础学生若第3次仍不能手算和追踪变量，先保留单窗口，增加支持课；不为了按时交付而由成人接手核心逻辑。

两人协作时，每20–30分钟交换“操作/检查”职责，两人分别回答一个代码问题。独立完成时，由家长或同伴担任一次读者即可。

## 6. 编程任务和 AI 导师用法

### 6.1 最小文件与版本

初版可将 HTML、CSS 和 JS 放入一个 `index.html`，减少多文件负担；功能稳定后才按需要拆分。教学目标集中在下列函数职责，名称可自行调整：

| 函数职责 | 输入→输出 | 学生必须理解的部分 |
|---|---|---|
| 校验与排序 | 原始列表→有效的排序副本或明确错误 | 哪些值无意义；并列如何处理 |
| `simulate(customers, policy)` | 客人列表、策略→逐人结果 | 选窗口、算开始时间、更新可用时刻 |
| `summarize(rows)` | 逐人结果→三项汇总 | 总等待/人数、最长等待、最大完成时刻 |
| `render(rows, summary)` | 结果→网页表格与说明 | 显示单位；数据来自计算结果 |

版本目标：v0.1 单窗口正确；v0.2 两种策略正确；v0.3 比较和输入校验可用；v1.0 完成试课后的修订与文档。页面美化排在计算、数据和解释之后。

### 6.2 给 AI 的启动提示词

> 我在做“排队侦探”标准研学项目，选择的场景是【学生填】。请按 fineSTEM 现有九阶段引导。先帮我把问题和比较条件说清，每次只问一个关键问题。开题时不要直接给完整程序。进入编码后，一次只帮助一个函数，先让我预测结果，再给必要提示或局部示例。我的原始数据、手算、代码改动、测试和反思要分别记录；缺失的结果标“待补”，不要编造。课结束时帮我整理“今天决定了什么、依据是什么、接下来测什么”，让我确认后保存。

### 6.3 阶段内提问

| 时机 | AI可以问 | 孩子要回答/操作 |
|---|---|---|
| 开题 | “你想比较平均速度，还是最久等候的人？” | 选指标，并说明原因 |
| 设计 | “一个窗口第30秒空闲，客人第20秒到达，何时开始？” | 回答30秒、等待10秒 |
| 编码 | “去掉 `max`，这组输入会出现什么？” | 先预测，再运行验证 |
| 调试 | “是哪一名客人的哪一列第一次和手算不同？” | 定位最早差异，避免盲目重写 |
| 实验 | “改变策略时，你还改了哪些条件？” | 核对到达/服务数据和窗口数 |
| 结论 | “哪条数据支持这句话？什么情况可能不适用？” | 指向E编号，说明范围 |

如果AI给出完整代码，仍要求孩子完成至少一处核心规则修改、一个新测试和逐步追踪；该帮助记录在AI使用说明中。不能以删掉AI痕迹的方式制造独立完成的表象。

## 7. 可直接执行的实验协议

### 7.1 标准版：四个固定情景

所有时刻/时长单位为秒，均为合成数据。每个情景同一份输入分别运行A和B。下面的预期值供教师校验，学生先预测、后核对。

| 情景 | arrival数组 | service数组 | A：平均/最长/完成 | B：平均/最长/完成 |
|---|---|---|---|---|
| S1 同时到达、服务一致 | `[0,0,0,0]` | `[10,10,10,10]` | 5 / 10 / 20 | 5 / 10 / 20 |
| S2 同时到达、首人较慢 | `[0,0,0,0]` | `[60,10,10,10]` | 17.5 / 60 / 70 | 7.5 / 20 / 60 |
| S3 到达稀疏 | `[0,30,60,90]` | `[10,10,10,10]` | 0 / 0 / 100 | 0 / 0 / 100 |
| S4 短时集中到达 | `[0,0,1,1,2,2]` | `[8,8,8,8,8,8]` | 7 / 14 / 24 | 7 / 14 / 24 |

操作：记录实验日期、代码版本、策略定义、输入ID → 预测 → 运行A/B → 保存逐人输出 → 核对汇总 → 写一句解释与一个局限。确定性输入重复点击不会产生新的独立证据，不以运行次数充当样本量。

学生另设计S5：至少改一个场景条件，先预测再运行。例如“不是第一人慢，而是第三人慢”。S5与S1–S4区分，不能事后只保留支持猜想的情景。

### 7.2 进阶版：多次随机情景

自选并说明一种到达与服务时间生成规则，例如到达间隔从0–5秒均匀抽样并累计，服务时间从5–20秒整数均匀抽样。每次生成一批20人，保存原始列表；做10批探索性模拟。它们只是教学分布，不声称符合真实饭堂。

每批输入配对运行A/B，报告每批的平均等待差、10批差值均值及范围。使用固定随机种子或保存后的数据文件复现；不能让A/B各自生成数据。10批只用于观察变化，不据此做普适优劣或统计显著性宣称。不同分布的敏感性分析作为进一步研究。

### 7.3 若采集真实观察

先确定可观察且获允许的场景，不干扰排队；只记匿名序号、到达/开始/完成相对时刻与观测说明，不拍可识别的人脸和身份信息。若无法完整观察同一个人的三个时刻，就标为缺失，不靠猜补齐。保留现场原始记录与清洗记录，不与合成数据混放。

现实中人会选短队、换队，窗口速度也可能不同。将实测数据输入当前模型只能做“在这些输入和简化规则下”的比较；要评估真实规则效果，需要另行设计观察或试点。

## 8. 验收清单

| 测试 | 预期 |
|---|---|
| 单人arrival=5、service=10 | 两策略等待0、开始5、完成15 |
| 两人同时到达，两个空窗口 | 两人均不等待 |
| S1–S4 | 与上表逐项一致，逐人表也能核对 |
| 空列表 | 显示“请添加数据”，不出现NaN；平均等待不伪装成实测0 |
| 负到达、0/负服务、非数值、Infinity、NaN | 明确拒绝并指出哪条数据；不继续生成误导结果 |
| 乱序到达 | 正确排序；同到达时按预定编号规则 |
| 重复运行 | 同一版本、同一输入、同一策略结果一致 |
| 连续运行A再B，再反序 | 输入不被策略修改，结果不依赖运行先后 |
| 学生口头验证 | 能追踪四人例中一个客人的start/wait/finish |
| 学生修改验证 | 能改一个服务时长，预测影响并复测 |

教师课前必须在计划使用的 fineSTEM 环境中走通：创建标准项目、按阶段保存工件、运行网页、保存证据、导出资料。这里给出的是验收条件，不代表这些测试已经在产品中执行。

## 9. 最终研究短文：填实际结果再写

建议题目：《固定窗口数下，两种排队策略的等待时间比较》。

1. **问题与背景**：为什么选这个场景，比较的具体问题是什么。
2. **假设与模型**：两个策略、窗口数、服务规则、排除的现实因素。
3. **方法**：输入来源、四个固定情景与学生自拟情景、代码版本、指标。
4. **结果**：逐项表格；选择一张图；每个结果标E编号。
5. **讨论**：哪些情景有差异、哪些无差异；平均更优是否每个人都更优；手算和程序是否一致。
6. **局限与下一步**：模型哪里简化；要回答真实场景，还需要什么数据。
7. **参考与AI说明**：引用实际阅读材料；说明AI帮了哪些部分，自己验证了哪些部分。

可用结论句型：“在【输入与规则】下，指标【名称】出现【已核验结果，E编号】。这支持/未支持我对【具体情景】的猜想；由于【限制】，还不能推断【更大范围】。”

没有实施时保留“待实验”。学生发现结果一样或与猜想相反，也可以形成完整报告。

## 10. 家庭对话与展示

家长在开始前先理解“等待时间不包括正在接受服务的时间”；过程中帮助孩子记录和解释，不接管算法；结束后提供一个真实疑问，例如“我等得更久了，为什么你说整个系统更好？”

三分钟展示建议：30秒讲问题，60秒演示同一输入的两种策略，60秒讲一个发现和一次改错，30秒讲局限。随后留两分钟接受问题。研究成果先在家庭或小组范围展示；如后续用于运营，另核对孩子与监护人的展示意愿及匿名范围。

## 11. 案例的运营出口

家长短视频讲“平均更快，可能仍有人等得更久”，用它讨论怎样向孩子追问依据。家长播客若制作，深入公平、效率、规则和模型边界。少年讲解展示输入、规则、手算、运行差异；任务页让孩子亲自改S5。完整配套见[运营执行方案](04_Know与运营执行方案.md)。
