# 学习目标、复刻改造与助教执行规范

日期：2026-11-02｜V3补充规范｜适用于线上自助主题sample，优先用于生态岛。

## 1. 项目的完整定义

一个主题sample既是可玩的作品，也是可由人类助教或AI agent引导复现、理解和改造的项目样板。孩子完成后应拥有：

- 可运行、可展示的个人作品和源代码。
- 能解释、能修改、能验证的编程与算法知识。
- 开题、拆任务、安排顺序、跟踪问题、控制范围和复盘的项目管理经历。
- 与作品有关的其他学科和科普知识。
- 从开始到结束可追溯的docs，以及可用于汇报的成品文档。

继续沿用六件套：可玩的作品、领域知识、自助创作路径、完整过程档案、家长视频、家长博客。新增“复刻教学包”和“助教执行规范”作为自助创作路径的必备组成。

所有核心步骤可由单个孩子在线完成。人类助教为可选支持；AI agent按相同任务规范提供帮助。家长内容独立成立，不要求家长担任老师。

## 2. 五条学习线与生态岛中的证据

| 学习线 | 要学到什么 | 生态岛中的实际任务 | 怎样判断学会 |
|---|---|---|---|
| 编程 | 数据、变量、条件、循环、函数、事件、状态、调试 | 表示岛屿状态，连接开始/暂停，修改环境事件 | 能解释一段关键代码，改动后预测并检查结果 |
| 算法 | 把规则写成步骤，理解输入输出、执行顺序、边界与比较 | 设计一次模拟更新：读取旧状态、计算变化、约束范围、生成新状态 | 能用小数据手推一次更新；说明换顺序可能造成什么差异 |
| 项目管理 | 目标、范围、任务拆解、依赖、里程碑、问题和变更管理 | 先跑通状态更新再做画面；记录卡点；决定新增功能是否影响当前目标 | 有实际使用的任务板和变更记录，能解释一次取舍 |
| 学科与科普 | 生态关系、资源限制、变化过程、数学表达、证据与模型 | 根据资料解释模型关系，读时间线，讨论简化条件 | 用自己的话解释概念，区分真实知识、教学设定与模拟结果 |
| 文档与表达 | 开题、设计说明、实验记录、技术讲解、结论与反思 | 记录关键决定，整理运行证据，完成作品介绍与汇报 | 关键主张有依据，能展示作品并回答关于规则和改动的问题 |

这些是设计目标，不保证仅因完成页面操作就自然达成。通过孩子的解释、修改和记录检查实际掌握程度。

## 3. 两轮学习：理解式复刻，再有理由地改造

### 第一轮：复刻参考项目

目标是让孩子走过“项目怎样从问题变成作品”，建立可运行的基础，并能解释其核心机制。

1. 试玩成品，理解它想回答的问题。
2. 阅读作者开题与知识导读，写下自己的理解。
3. 看懂最小范围，把工作拆成有顺序的任务。
4. 从起始代码逐步完成关键部分，而不是一次粘贴全部代码。
5. 对照已知例子测试，定位一次问题，保存版本与记录。
6. 讲解自己的复刻版本：哪些由自己完成，哪些参考作者，哪些由AI帮助。

复刻阶段如实标注参考关系。项目名称可标“基于生态岛sample的学习复刻”，不包装成原创研究。参考实现可查看；每次查看后仍需解释和验证。

### 第二轮：改造自己的项目

目标是让孩子开始作出自己的决定，形成属于自己的问题和成果。

1. 自选一个改造理由：想研究的新问题、希望改善的体验或想表达的新故事。
2. 写一张小变更单：改什么、为什么、影响哪些模块、怎样验收。
3. 更新任务板与计划，保留复刻版作为对照。
4. 实现变化，记录预测、结果与必要的修订。
5. 用原版与新版的对照说明变化是否达到目标。
6. 完成个人作品、报告和汇报材料。

可选层级：

| 层级 | 改造举例 | 对应学习要求 |
|---|---|---|
| 入门 | 改初始资源、动物数量或参数范围，比较变化 | 理解参数含义，能记录和解释差异 |
| 标准 | 将固定资源补充改为阶段性规则；增加一个环境事件 | 修改条件/函数，检查边界和执行顺序 |
| 进阶 | 新增关系或机制；把多个事件设计成交互故事 | 调整数据与模块，解释模型或叙事依据，补充测试 |

入门修改可以作为阶段完成点。完整项目至少包含一项有理由的规则、功能或表达改动；仅换皮肤不作为全部学习证据。并非所有孩子都必须完成进阶扩展。

## 4. 生态岛复刻的六个里程碑

下表是功能与学习节点，不是固定课表。领域知识穿插在相应任务前后学习。

| 里程碑 | 完成的功能 | 需要理解的知识 | 项目管理动作 | docs自然增加什么 |
|---|---|---|---|---|
| M0 问题与计划 | 明确要复刻的范围、成果和工具 | 生态岛的关系与模型边界 | 建任务板，排最先三个任务 | 开题、资料、计划 |
| M1 静态世界 | 显示草、水、动物和状态 | 数据字段与含义；界面是状态的表达 | 拆开数据与显示任务 | 数据字典、设计草图 |
| M2 世界会变化 | 单步推进并显示新状态 | 函数、条件、更新顺序、资源限制 | 先验证规则，后接动画 | 算法说明、手推与测试 |
| M3 可以控制 | 开始、暂停、重置、环境事件 | 事件、状态、时间步 | 记录并解决控制逻辑问题 | 调试与版本记录 |
| M4 可以研究 | 保存配置、显示过程、比较结果 | 数组、历史记录、对照、指标含义 | 检查范围，冻结复刻基线 | 运行配置、数据、试验记录 |
| M5 可以解释 | 作品说明、知识入口、模型限制 | 信息组织、引用、科学表达 | 验收复刻，制定改造单 | 代码讲解、复刻总结 |

每个节点提供：可运行起点、目标、所需知识、具体任务、分级提示、自查、检查点代码、常见错误、记录提示。检查点代码是恢复工具，不能代替理解检查。

## 5. 单人项目管理怎样教

用轻量任务板：待办、进行中、卡住、完成。建议同时推进一个主要任务，减少“已经做了很多但没有一项能运行”。

任务卡模板：

- 任务ID与目标：
- 为什么现在做：
- 依赖什么：
- 预计需要多少时间：
- 完成标准：
- 当前状态与卡点：
- 实际用时与调整原因：
- 对应代码版本和证据：

示例：“让重置按钮恢复到初始岛屿”。依赖是已有配置与状态；完成标准是任意运行后点击重置，状态、模拟步数、历史记录均回到约定起点。孩子据此理解任务应当可以检查。

至少经历一次范围取舍。比如想加第二种动物时，先判断是否需要新增食物关系、状态字段和测试；可以进入下一版待办，不必为了新想法打断当前里程碑。

估时用于学习安排工作，不用于催促。计划允许改变，关键是说明原因，并更新下一步。无需先学复杂项目管理术语或团队职位。

## 6. 全程docs：有记录，但不反复填表

一个项目包分为代码与文档。以下为建议逻辑结构，落实时应对接fineSTEM现有阶段工件和存储，避免另建重复的事实来源。

| 文档/材料 | 何时形成 | 谁负责原始内容 |
|---|---|---|
| README：作品简介、运行与版本 | 开始写一句话，结尾补完整 | 孩子确认 |
| 开题：问题、目标、范围、验收 | 开始；改造时补充 | 孩子选择，助教协助收窄 |
| 知识与资料卡 | 每次阅读和学习 | 引用真实来源，孩子写理解 |
| 计划与任务板 | 开始创建，过程持续更新 | 孩子估时与取舍 |
| 设计与算法说明 | 实现前写草案，修改时更新 | 孩子解释，助教整理 |
| 开发、调试与版本日志 | 关键改动、失败和修复时 | 系统事实加孩子原因说明 |
| 数据、配置与测试记录 | 每次正式比较或验收时 | 实际输入、输出和版本 |
| 变更单与前后对照 | 从复刻转向改造时 | 孩子提出并确认 |
| 结题/研究报告 | 基于已有记录整理 | 孩子确认结论与局限 |
| 汇报材料 | 项目结束 | 从报告和作品中提炼 |

自动记录适合保存时间、版本、输入、输出等事实；人类或AI助教可以摘要和组织。问题选择、预测、修改理由、结论与反思应保留孩子自己的表达。每次关键步骤只补少量记录，结题时汇总，不让文档变成另一套重复作业。

沿用已有九阶段工件：开题对应project_brief，范围对应constraints，技术与设计对应track_plan/design，任务对应step_plan，过程对应dev_log，结题对应evaluate，代码讲解对应explanation。实验数据和代码快照作为附件关联。这里是对接建议，未确认当前导出已经完整支持。

## 7. 人类助教与AI agent共用的引导规范

助教每次先读取当前阶段、任务、版本、已有证据与最近卡点，再决定下一步，不能只凭最新一句话重新生成整个项目。

一次引导循环：

1. 说明本次小目标，以及它在项目中的作用。
2. 让孩子说想法或预测；必要时先讲领域或代码知识。
3. 提供一个可以亲手完成的任务。
4. 查看实际结果，要求孩子解释关键差异。
5. 对照自查标准，决定继续、补学或修复。
6. 更新任务状态和必要记录，指出下次从哪里继续。

帮助逐级增加：提问和观察线索→概念/伪代码→局部示例→参考实现。若直接展示参考代码，也应让孩子追踪、改动并验证，记录帮助程度。

助教不能把“运行成功”自动当作“已经学会”。也不能伪造执行结果、自动编造反思或用通用结题文字掩盖证据缺失。

### 任务卡的助教字段

任务ID、前置知识、前置成果、目标、学生动作、分级提示、预期可观察结果、边界测试、理解问题、需保存记录、常见错误、恢复入口、下一任务。

同一套字段可供人类阅读，也可作为AI agent的结构化任务上下文。初版使用Markdown即可，不先强依赖开发教学编排系统。

### 生态岛的一次引导示例

目标：增加“干旱事件”，暂时改变资源补充规则。

- 先问：干旱在这个教学模型里改变什么？为什么不直接让动物数量立即减少？
- 孩子确认规则和假设，再定位负责资源更新的函数。
- 让孩子预测触发与未触发的两次运行会有什么差别。
- 只提供当前需要的条件判断或事件示例。
- 同一初始条件分别运行，核对事件的开始、持续与结束。
- 让孩子说明实际结果及模型省略的因素。
- 保存变更、配置、版本、结果，更新任务板。

这只是教学情境，不是已验证的生态机制或实际学生记录。科学解释需与最终确定的模型和来源一致。

## 8. 最后交付与验收

### 展示包

- 可运行作品与源代码，说明如何开始、重置和查看结果。
- 作品简介，说明参考来源、自己的改动和适用边界。
- 一段可直接照着进行的演示顺序；录屏可选，不要求孩子出镜。

### 汇报包

- 结题报告：问题、知识、计划、设计、实现、验证、改造、发现、局限、反思。
- 简短汇报提纲：为什么做→怎样做→学到什么→改了什么→证据是什么→还想研究什么。
- 过程附件：代码版本、资料、任务板、数据和调试记录。
- 若开展了范围明确的研究，形成专题短文；创作类则形成创作研究说明。

建议汇报可以用网页、Markdown或后续导出的文档呈现；PPT不是完成的必要条件。导出为PDF/Word等格式的可靠性需在产品实际验证。

验收分别看“作品完成”和“学习证据”：

| 检查 | 基本通过标准 |
|---|---|
| 作品 | 可运行，主要功能与说明一致 |
| 编程 | 能解释关键输入输出，并完成一处有效修改 |
| 算法 | 能手推一个小例子，说明规则顺序和至少一个边界 |
| 项目管理 | 能展示实际用过的任务板，解释一次安排或变更 |
| 领域知识 | 能解释相关概念，并指出模型的一项限制 |
| 文档 | 开题、过程、版本、结果与结题连得起来 |
| 个人贡献 | 能区分参考、AI帮助和自己的判断/实现 |

如实记录尚未掌握的内容及下一步，不用漂亮成品或长篇报告覆盖理解不足。

## 9. 制作者需要补齐的交付

生态岛的制作交付在六件套之外进一步细化：

- 作者完整参考工程及真实制作档案。
- 起始代码与M0–M5检查点。
- 知识和算法讲解材料。
- 每步孩子任务卡、助教引导卡、自查和排错卡。
- 标准规则/功能改造任务与进阶开放任务。
- 空白docs模板与填好的作者示例。
- 作品验收、理解检查和最终汇报模板。

本次只补充策划与执行标准，尚未编写生态岛代码、制作教学媒体或实现助教编排功能。后续制作应按这些标准形成一套真正可以复刻、改造和汇报的sample。
