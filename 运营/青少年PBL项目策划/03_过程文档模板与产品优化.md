# 过程文档、研究短文模板与 fineSTEM 优化建议

> V1支撑材料：证据与写作模板可继续使用。V2还需纳入场地调查、访谈、阅读、实体模型及设计取舍，见[当前课程方案](06_V2_一平方米未来城市_课程方案.md)。

日期：2026-10-19｜v1.0｜本文件提供可人工使用的模板；新增字段和功能均为产品建议。

## 1. 文档随研究生长

每次活动结束花3–5分钟，记录“做了什么、为什么这样做、证据在哪里、下一步是什么”。AI整理，学生确认。下列文档可由一次记录生成多个视图，不能要求孩子重复填同一信息。

最后三种交付各有用途：开题报告说明计划；技术说明让别人理解与复现；结题研究短文解释实际发现。最终短文从已验证记录组织出来，缺证据的地方标待补，不靠生成文字填满。

## 2. 对接当前九阶段

阶段和工件名取自 `apps/backend/app/services/stage_constants.py`，中文教学任务为本次设计。

| 当前阶段 | 当前工件/文件 | 孩子记录什么 | 教师检查什么 |
|---|---|---|---|
| stage_00_bootstrap 初始化 | 无必需工件 | 年龄段、先备、可用时间、项目兴趣 | 难度和环境是否适配 |
| stage_01_brainstorm 脑爆 | brainstorm / 00_brainstorm.md | 观察、问题候选、选择理由 | 是否有自己的问题 |
| stage_02_brief 开题 | project_brief / 01_project_brief.md | 驱动问题、假设、指标、产物 | 假设与结论分开 |
| stage_03_constraints 范围 | constraints / 02_constraints.md | 做与暂不做、时间/材料限制、简化假设 | 是否能在工时内完成 |
| stage_04_track 技术 | track_plan / 03_track_plan.md | 语言、运行方式、已有能力与待学知识 | 技术是否服务于问题 |
| stage_05_design 设计 | design / 04_design.md | 数据结构、方法、流程、测量/实验规则 | 输入输出可检查 |
| stage_06_step_plan 计划 | step_plan / 05_step_plan.md | 任务顺序、负责人、验收、预估时间 | 每步有可见产物 |
| stage_07_execute 编码 | dev_log / 06_dev_log.md | 版本、测试、实验、失败、修改 | 证据能关联到版本和输入 |
| stage_08_evaluate 验收 | evaluate / 07_evaluation.md | 结果、反馈、反思、结论与局限 | 结论可追溯，学生能解释 |

数据、图表、源材料、研究短文作为附件或证据关联；不擅自添加新的阶段门禁。九阶段按现有顺序推进；后期发现设计不足时，通过修订记录说明，不要求回退到旧阶段才能修订思想。

## 3. 学生可复制的填写模板

### A. 一页开题卡

```markdown
# 项目开题卡
项目ID/名称：
作者或小组代号：
日期/版本：

## 我遇到的现象
我观察到：
我选择这个问题是因为：

## 我想回答的问题
在什么条件下，比较什么，观察什么：

## 我的猜想
我猜：
理由是：
如果出现什么结果，我会改变想法：

## 我会学到什么
领域知识（最多3项）：
需要理解并修改的代码（最多3项）：

## 我准备怎样研究
比较的方案：
保持相同的条件：
输入/数据从哪里来（实测/公开数据/合成）：
看哪些指标，单位是什么：

## 我准备交付什么
最小作品：
成功标准：
暂不研究：
计划时间和材料：
展示给谁：
```

### B. 知识与代码理解卡

```markdown
概念名称：
这个概念帮助我解决项目中的什么问题：
用自己的话解释：
一个小例子：
我认为容易搞错的地方：

代码文件/版本/函数：
输入是什么：
输出是什么：
我逐步追踪的例子：
我改了哪个值或规则：
运行前的预测：
运行后的实际结果与证据ID：
两者不同，我怎样解释：
AI/老师帮助了什么：
```

### C. 数据来源卡

```markdown
数据集ID：
类型：实测 / 公开数据 / 合成 / AI生成示例（选择并说明）
来源、采集人或生成方法：
采集/生成日期：
如来自网页，原始URL和访问日期：
字段、单位、取值范围：
样本量和一行代表什么：
采集/生成条件：
缺失、异常以及处理规则：
原始文件位置：
清洗后的文件位置和版本：
可以用来回答什么：
不能据此回答什么：
```

原始数据保留不覆盖。修改、删除异常行必须写理由，并保留修改前后的版本。合成数据可以用于算法测试和模型探究，不能写成现场观测。

### D. 实验记录

每次实验使用一行索引，详情和输出可放附件。

| 实验ID | 日期 | 问题/假设 | 代码版本 | 数据集ID | 策略/参数 | 运行前预测 | 结果文件/证据ID | 异常与解释 |
|---|---|---|---|---|---|---|---|---|
| 待填 | | | | | | | | |

比较实验补一张表：

| 情景/批次 | 保持相同的条件 | A指标与单位 | B指标与单位 | 差值定义及数值 | 是否支持猜想 | 适用范围 |
|---|---|---|---|---|---|---|
| 待填 | | | | | | |

没有运行就写“未运行”，不要填0。不存在的指标写“不适用”，与缺失分开。

### E. 调试与修订记录

```markdown
记录ID/日期：
问题发生的代码版本：
输入与复现步骤：
我原本以为会发生：
实际发生：
第一次不同的位置：
我的原因猜测：
我改了什么、为什么：
AI/同伴给的建议：
修改后版本：
同一用例复测结果：
补测了哪个其他用例，结果是什么：
我仍不确定：
证据ID：
```

“AI修好了”不是完整记录；至少说清错在哪里、改了什么、怎样知道改对了。为教学故意设置的错误必须标“预设练习”，不包装成学生真实遇到的事件。

### F. 反馈与反思

```markdown
展示对象与日期：
对方最关心的问题：
对方提出的一个质疑或建议：
我接受/不接受的理由：
我补做了什么：
补做后的结论变化：
我能够独立完成什么：
我仍需要帮助什么：
如果再做一次，先改哪一步：
```

### G. 研究短文模板

```markdown
# [围绕实际比较问题命名]
作者代号：
日期：
项目及代码版本：

## 摘要（最后写，约100–200字）
研究的问题、方法、实际结果、适用范围。没有结果时保留待补。

## 1. 问题与背景
问题来源；已知知识；我为什么选择这个问题。

## 2. 假设与研究方法
可改变/保持不变的条件；样本；数据来源；模型假设；
算法或测量方法；指标定义与单位；代码版本；复现步骤。

## 3. 结果
结果表格、图表与必要描述。每项关键结果附证据ID。
同时保留无差异、反例、失败或异常，不只展示有利结果。

## 4. 讨论
结果与最初猜想是否一致；可能原因；哪些证据尚不足；
模型和现实差别；不能推出什么；下一步如何验证。

## 5. 结论
限定范围内能回答什么；仍未回答什么。

## 参考资料
实际阅读的来源、标题、URL或出版信息、访问日期。
没有查阅的文献不列入，不由AI补造参考文献。

## AI与其他帮助说明
工具/模型（知道则填写）、使用日期、帮助的环节；
学生的选择、修改和独立验证；成人或同伴的具体帮助。

## 附件
数据字典、原始数据、实验表、代码版本、测试、修订与反馈。
```

标准版可称“项目研究短文”或“小研究报告”。工程项目也可以使用“设计问题—备选方案—原型—测试—改进—局限”的结构；不为凑论文结构强行虚构研究假设或效果数据。

## 4. 证据如何支持结论

证据分三类：项目事实（学生选择、修改、反馈）；实验事实（输入、代码、输出）；外部知识（书籍、官方资料、论文）。AI对知识的解释本身不能替代可查来源。

| 证据ID | 类型 | 内容摘要 | 阶段 | 关联版本/数据 | 原文件 | 确认状态 |
|---|---|---|---|---|---|---|
| E01 | 项目事实 | 待填写真实观察/选题来源 | 选题 | — | 待填 | 待学生确认 |
| E02 | 实验事实 | 待填写一次实际运行结果 | 编码 | 待填 | 待填 | 待复核 |

再做“结论—证据”映射：

| 结论草稿 | 所需证据 | 现有证据 | 状态 | 写入报告的处理 |
|---|---|---|---|---|
| 在S2中B的平均等待更短 | S2输入、A/B输出、对应代码版本 | 待实际运行后填 | 待验证 | 暂不写成学生发现 |
| B在现实中一定更好 | 不同真实场景的可靠验证 | 当前不具备 | 超出范围 | 删除或改为下一步问题 |

**复现最小包**：输入数据 + 代码快照 + 策略/参数说明 + 原始输出 + 环境/依赖说明 + 简短操作步骤。仅截图不足以复现。

## 5. 当前文档实现的具体缺口

本地 `document_service.py` 的 `_snapshot` 获取项目、技能状态、证据和成果卡；`_build_markdown` 输出通用摘要，并为开题、技术、结题附重点提纲。证据在快照查询中上限1000，正文只取前50条、每条最多120字符；在已检查的该导出路径中，未见按九阶段工件展开正文、完整附件索引或结论级引用组装。

这说明当前导出可作为摘要，但是否保存齐全、是否生成了有实质内容的研究短文，需要额外检查。其他工作区工件链路与这条导出路径应一并梳理，不能只改导出标题。

## 6. 产品优化优先级与验收

以下为待开发建议；本次没有修改这些功能。

| 优先级 | 功能 | 解决的问题 | 可验收结果 |
|---|---|---|---|
| P0 | 阶段工件、完整证据与附件统一组装 | 导出只有概况和摘要 | 已填写的各阶段正文能进入对应报告；任何摘要截断都能链接到完整原件 |
| P0 | 证据ID、代码版本、数据版本关联 | 结果无法对应实现 | 每条实验结果能找到输入、参数、代码快照和输出；重复运行保留独立记录 |
| P0 | 实测/公开/合成/AI示例标签 | 数据类型混淆 | 每张结果表带来源类型；合成数据不会自动表述为现场调查 |
| P0 | 缺项与待验证标识 | AI用流畅文字填补空白 | 无结果不生成效果结论；无出处不生成引用；缺失项可定位到补做任务 |
| P0 | 学生确认与生成快照 | AI整理改变原意、报告与版本脱节 | 保留学生原话、AI整理版及确认状态；报告记录所用材料版本 |
| P1 | 结论—证据映射与点击回溯 | 结论难以核查 | 每个关键结果有引用ID；移除证据后对应段落提示失效 |
| P1 | 三种报告视图 | 同一内容重复填表 | 同一份已确认材料生成开题/技术/结题，章节按目的组织 |
| P1 | 图表数据绑定与单位检查 | 图表漂亮但数值不可核对 | 从图表可查看对应原始表；单位缺失或不一致有提示 |
| P1 | AI贡献与学生理解记录 | 成品无法体现实际学习 | 能看到学生预测、改动与复测，报告附帮助说明 |
| P2 | 学科/年龄模板、多格式排版、展示卡 | 不同项目写作负担和样式差异 | 同一证据适配不同表达；格式转换不丢表格、附件和来源 |

首轮可先人工执行同一规范：每课导出或保存一次版本；证据编号写入日志；用Markdown模板汇总；学生逐项确认后再导出成品。这样试课可以先进行，也能为产品开发提供真实缺项。

## 7. 文档质量检查

提交前逐项核对：题目和问题一致；方法能复做；数据类型明确；所有数值有来源；代码版本明确；至少一次真实修订或如实记录无修订理由；有学生原话；讨论局限；列实际查阅来源；AI帮助已说明。未完成项保留状态，不通过“补写得像做过”来解决。
